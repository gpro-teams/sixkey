## 1. 用户看到什么

> 已被 §18.1 取代（开关、14 天、`rsLock`、`rsPaused` 都没有了）。

**设置 › 安全 › PIN 快速解锁**（只在设置页解锁、PIN 已设置时，展开的 PIN 框里）：

- 一个开关"**重启后也可以**"（en "Also after a restart"，与 Touch ID 那一栏的开关同名，复用 `dvAlsoRestart`），**默认关闭**。
- 开关下面始终有两行：`dvDue`"Sixkey 每 14 天请你输入一次主密码，免得忘记。"，以及所有者原话的提示框
  `rsCost`"拿到这个浏览器配置文件副本的人可以离线猜你的 PIN；PIN 越长越难猜。"（"这个浏览器配置文件"与 Touch ID 的用词一致，
  维护者 B 方案①）。打开之前就能看到代价。
- PIN 几位都可以开：规则和普通 PIN 完全一样（4 到 8 位数字，弱 PIN 照普通规则拒绝），4 位 PIN 也是勾上、输主密码、完成。
  开关不会因为 PIN 的位数灰掉，也没有讲位数的那行字（2026-10-30 所有者决定，§17；原来少于 6 位时开关灰掉、下面一行 `rsSix`
  "PIN 至少 6 位。"，已删除）。
- 打开：勾上 → 出现主密码框和"开启"按钮 → 主密码对了就开启；错了照常报错并记入安全记录（`unlock_failed`）。
- 开启后 PIN 框的状态行：`pinOn`"已开启（〈位数〉 位）。在 〈上次输主密码 + 14 天〉 之前可以用它打开 Sixkey。"
- 开启时改 PIN：新 PIN 只按普通 PIN 的规则检查，4 位也可以；改完用新 PIN 重做记录，开关仍开着（2026-10-30 起，§17；原来少于
  6 位时输入框下提示"PIN 至少 6 位。"、服务端答 `short_pin`，已删除）。
- 关闭：取消勾选，记录立即删除，不问密码（只是拿走一条路）。
- 暂停（换了密钥或主密码）或等主密码（14 天到了、输错 5 次、点过"立即结束快速解锁"）：开关仍是勾着的，下面出现
  "重新开启"（`dvTurnOn`）。暂停、且是本页刚换的密钥（10 分钟内）：输 PIN 即可；输错一次就改为要主密码
  （`dvFailed`"未能完成，请使用主密码。"）。其他情况：输主密码。
- "立即结束快速解锁"按钮：记录可用时也显示（锁定状态下也有）。
- `secInvTitle`"Sixkey 在这个浏览器配置文件里保存的内容"清单里，记录存在时多一行：
  "**PIN 快速解锁 · 重启后也可以** 拿到这个浏览器配置文件副本的人可以离线猜你的 PIN；PIN 越长越难猜。"（全用现有的词拼成）。
- 共享或由脚本控制的配置文件：PIN 框本身就说不可用（`pinShared`），开关不出现。
- `pinLead` 改写（维护者 D 方案：开关打开后原句"只到浏览器关闭为止"不再是事实）：
  zh "4 到 8 位数字的 PIN 可以在 Sixkey 锁定后重新打开它，默认到浏览器关闭、最多上次输入主密码后 12 小时。不要用手机或银行卡的 PIN。"
  （76 字，原句 87 字）；en "… by default until the browser closes, at most 12 hours after you last typed the master password. …"
  （189 字符，原句 209）。两种状态下都成立；开关的情况由紧挨着的开关和两行说明交代。`pinHonest`、`pinRoot`、`pinOn`、
  `pinWaiting`、`pinClose`、`pinShared`、`quickEnded` 逐句看过，开关打开后仍然属实，未改。

**锁屏**（弹窗、侧边栏；设置页的解锁条同样先会话后记录、PIN 框来自记录，但不显示下面两句，开关打开时也不显示 `lockPinWaiting`）：

- 浏览器重启或扩展重新加载（包括商店更新）之后：锁屏**直接是 PIN 框**，剩余次数取自记录。输 PIN 后转盘转动、表单
  `aria-busy`，派生在 WebCrypto 里异步进行，页面不卡（e2e 实测：派生期间页面照常响应，§9）。
- 输错：显示剩余次数。第 5 次输错：切到主密码，下面一行 `rsLock`"超过 14 天或输错 5 次后，PIN 需要先输一次主密码。"
- 14 天到了：锁屏直接是主密码，下面同一行 `rsLock`。
- 换了密钥或主密码：锁屏是主密码，下面一行 `rsPaused`"密钥或主密码已更换，PIN 快速解锁的"重启后也可以"已暂停，需在设置中重新开启。"
  （en "Keys or master password changed: PIN quick unlock's "Also after a restart" is paused until you turn it back on in Settings."）
- 在锁屏输主密码解锁后：记录静默恢复可用（14 天重新计时；被拿掉的密钥材料重新做出来），之后锁定、重启都能用 PIN。
  **恢复密钥解锁不算**（不重新计时，也不重做），和 Touch ID 一样。
- 开关打开时，原来那行 `lockPinWaiting`"浏览器重启、扩展重新加载、超过 12 小时或输错 5 次后，PIN 需要先输一次主密码。"不再显示
  （不再属实），由上面两句取代；开关关闭时一切照旧。

这两句锁屏文字放在只有弹窗和侧边栏加载的目录 `restart-popup`（B 方案）；设置页的两句放在开关自己的懒加载目录 `restart`。

## 2. 记录与密码学

### 2.1 记录 `sk_pin_restart`（`chrome.storage.local`，只在本机，`LOCAL_ONLY_KEYS.restart`）

```
{ v: 1,
  id,              // 16 字节随机，base64；每做一次包装就换新的
  vaultId, vkId,   // 为哪个库、哪把库密钥做的
  setup,           // sk_pin 的 PBKDF2 盐：这条记录属于哪一次 PIN 设置
  wraps,           // 做记录时密钥环所有包装的 wrapsTag（pin.ts）：任何重新包装都会让它对不上 → 暂停
  mac,             // 见 2.2
  lastPasswordAt,  // 上次输主密码的时间（14 天，prf-record.ts passwordRecent，与 sk_prf 同一规则）
  fails,           // 连续输错次数 0..5，每次尝试**先**写
  wrap: { kdf: {name:"PBKDF2", hash:"SHA-256", iterations, salt, v:1}, iv, wrapped } | null }  // null = 密钥材料已删除
```

不是库数据（`store.ts hasAnyData` 不看它），不进镜像、快照、备份、导出、同步；关闭同步不动它。

### 2.2 构造（`src/core/crypto/pin-restart-wrap.ts`）

```
pinKek  = PBKDF2-SHA256(NFKC(PIN), sk_pin 的盐, 600,000 次)        // PIN 自己的钥匙（pin.ts derivePinKek），sk_pin 里也用 VK 封着一份
KEK     = PBKDF2-SHA256(pinKek, 记录自己的 16 字节盐, ≥ 2,000,000 次, 256 位) → AES-256-GCM，不可导出
wrapped = AES-256-GCM(KEK, 12 字节 IV, VK 的 32 字节,
                      AAD = "sixkey-pin-restart|1|{vaultId}|{vkId}|{id}|{setup}|{wraps}")
mac     = HMAC-SHA256(HKDF-SHA256(VK, salt=∅, info="sixkey/v1/pin-restart-mac"),
                      "sixkey-pin-restart-mac|1|{vaultId}|{vkId}|{id}|{setup}|{wraps}")
```

- **KDF 与参数。** 主密码在本机用的 KDF 是 **PBKDF2-SHA256**（`kdf.ts`：新包装 `PBKDF2_PASSWORD_WRAP_ITERATIONS = 2,000,000`，
  读取下限 600k、上限 20M），不是 Argon2id：仓库里没有 Argon2（PLAN §5.1 不用 wasm；`check-dist` 强制的 CSP 没有
  `'wasm-unsafe-eval'`）。所以这里用同一个 KDF、**不少于**主密码的次数：`restartIterations` 取 2M 与本密钥环任何主密码
  包装实际次数中的较大者（≤20M）。每次猜测要付 600k + ≥2M = **≥2.6M 次**，比猜主密码（2M）还贵。见 §12 偏离 1。
- **为什么两层。** KEK 从 pinKek 派生而不是直接从 PIN 派生：sk_pin 里有用 VK 封着的 pinKek，所以**主密码**（解开 VK）就能在
  不知道 PIN 的情况下重做包装（第 5 次输错、"立即结束快速解锁"之后，下次输主密码自动恢复）；同时攻击者每猜一个 PIN 仍要
  付两次派生。PIN、pinKek、KEK、解开的 VK 都不落盘、不记日志（测试逐路径检查 `chrome.storage.local`，§10）。
- **域分隔。** 三个新标签（`RESTART_TAG`、`RESTART_MAC_LABEL`、`RESTART_MAC_TAG`）只在本地，不是同步标签，与 PRF、门、
  PIN、会话、库密钥的标签都不同，互不为前缀（`contract-vectors`、`pin-restart-crypto` 测试）。
- **AAD** 绑定库、库密钥、记录 id、PIN 设置、密钥环包装，以及版本（标签里的 `|1|`）。KDF 参数不在 AAD 里：改了参数
  KEK 就变了，GCM 照样解不开。
- **MAC** 用 VK 派生的钥匙算，锁屏解锁前（没有 VK）不能验，所以它不挡"改了能不能打开"（那是 GCM 的事），它挡的是**重做**：
  主密码只为 MAC 对得上的记录重做包装，植入的记录永远不会被做成能打开的（§2.3 第 6 条）。
- **完整字段检查**（`restartOk`）：版本、各 base64 字段的确切字节数、vaultId/vkId 格式、0 ≤ fails ≤ 5、KDF 参数在 kdf.ts 范围内、
  wrap 恰好 3 个键、没有未知字段。派生、重做、写入之前都先过这一关。

### 2.3 篡改分析（对手：能写这个配置文件存储的人，没有 PIN 也没有 VK）

| # | 攻击 | 结果 | 测试 |
|---|---|---|---|
| 1 | 改写 wrap（IV、密文、盐、次数） | GCM 解不开，算一次输错；次数低于 600k 或超出范围：完整检查不通过，不提供 PIN，不计次 | crypto、service "rewritten record" |
| 2 | 改写头部（vaultId、vkId、id、setup、wraps） | 与当前密钥环 / sk_pin 对不上 → 不提供或"暂停"；改了 id 让它看起来对得上：AAD 不符，解不开 | 同上；mutants N5–N10 |
| 3 | 把一条记录的 wrap 换到另一条（另一库、另一密钥、另一 PIN 设置） | AAD 不符，解不开 | crypto "does not open with … any field the AAD binds changed" |
| 4 | 次数回滚（fails 改回 0）、14 天挪后 | **挡不住**：多给键盘前的人几次尝试 / 推迟提醒。能写存储的人也能直接复制记录离线猜，次数本来就挡不住他（§2.4）。与 Touch ID 的 14 天同样定性为"提醒，不是安全控制" | service "a counter rolled back …" |
| 5 | 整条记录回滚（关掉开关后、第 5 次输错后放回旧记录） | 密钥与 PIN 设置没变：**又能用**，挡不住（同 4）。密钥或 PIN 已换：旧记录对不上 → 暂停 / 不提供，永远不会被尝试。放回的旧记录是 Sixkey 做的（MAC 对得上），设置页显示为开（改 PIN 之前可以重新开启：主密码，或本页刚换完密钥时的 PIN）；**改 PIN 只沿用可用的记录**（这把 VK、这份 PIN 设置，状态 "pin" 或 "wait"），**暂停的一律删除**、不重做，不管是轮换还是改主密码等重新包装暂停的（r3 只管轮换：PINR-R2-04，第二轮审查 Q3；r4 扩到所有暂停的：PINR-R3-01，r3 复核 T1 复现）；删掉之后再开启只能输主密码（`turnBackOn` 答 `bad_state`，r4 后续 PINR-R4-01）。**挡不住的一种（r4 如实写明，PINR-R3-02）**：开关关掉之后，有人把当前密钥下的旧记录（包括 wrap 已被第 5 次输错或"立即结束"拿掉的，状态 "wait"）写回，下一次在锁屏输主密码或改 PIN 时，它会被重新做成能打开的记录（r3 复核 T2 复现）：Sixkey 分不清它和用户自己那条"等主密码"的记录，本地存储防不住回滚；要能反复改写并复制这个配置文件的人才能做到。所有者 2026-10-30 按推荐定为保持现在的设计（20 号文件补充问题 1 (a)） | service "a record of an older PIN swapped back …"；r2 "PINR-R2-04"（三条）、"PINR-R3-01"（四条）；mutants Y01–Y03、S01–S04 |
| 6 | 植入记录（随便填，或用自己的钥匙和自己的 PIN 做一条） | 头部字段都不是秘密，可以让锁屏提供 PIN 框；但植入者没有 VK，做不出能被用户 PIN 解开、又能通过密钥 id 检查的包装：用户输 PIN 只会算输错。任何会"用到"记录的地方都先在 VK 下验 MAC（r2，PINR-01）：主密码记账（r3 起在写任何东西之前，PINR-R2-01：r2 只在重做 wrap 时验，植入的、带 wrap 的记录会被主密码"续期"，第二轮审查 Q1、E1 复现）、改 PIN、设置页的状态（开关、PIN 框状态行、"保存的内容"清单）、重新开启；验不过 → **删除**（比对交换）、显示为关，永远不会被续期或做成能打开的（r1 漏了改 PIN：植入的空壳会被新 PIN 做成真记录，审查 E1 在真实 Chromium 复现） | service "a planted record …"（两条）、r2 "PINR-01"（四条）、"PINR-R2-01"（三条）、e2e "a stub planted …"（含清单）；mutants P1、C3、V1–V5、V14、W01–W04、M02、M04 |
| 7 | 降级：植入低次数参数 | 解不开（KEK 不同），攻击者也什么都得不到；重做包装从不沿用记录里的参数，总用 `restartIterations` | mutants N11–N13 |
| 8 | 让用户的 PIN 泄露 | PIN 只在 Sixkey 自己的锁屏输入，派生结果从不写出；没有可泄露的通道 | 源规则测试（无 console / diag 输出秘密） |
| 9 | 离线猜 PIN（拿到配置文件副本） | **挡不住**，这就是所有者接受的代价；成本见 2.4 | — |

### 2.4 离线猜测的代价（估计）

仓库沿用的数字：一张 RTX 4090 对 PBKDF2-SHA256 约 9×10⁹ 次迭代/秒（600k 次时约 15,000 次猜测/秒，PLAN §5.1，
QUICK-UNLOCK §1.7 [transcribed]）。每次猜测 ≥2.6M 次迭代 → 约 **3,500 次猜测/秒**（一张卡），**遍历全部** PIN 的时间：

| PIN | 可能数 | 2.6M（默认） | 20.6M（主密码包装若用到 kdf.ts 上限 20M） |
|---|---|---|---|
| 4 位 | 10⁴ | 约 **3 秒** | 约 23 秒 |
| 5 位 | 10⁵ | 约 29 秒 | 约 4 分钟 |
| 6 位 | 10⁶ | 约 **5 分钟** | 约 40 分钟 |
| 7 位 | 10⁷ | 约 48 分钟 | 约 6.5 小时 |
| 8 位 | 10⁸ | 约 **8 小时** | 约 2.7 天 |

独立审查用 RTX 5090 的已核实基准（1.11×10¹⁰ 次/秒，约 4,290 次猜测/秒）核算：6 位约 3.9 分钟、7 位约 39 分钟、8 位约 6.5 小时
（REVIEW.md §3；同一基准下 4 位约 2.3 秒、5 位约 23 秒，是 PIN4 补算的），与上表误差在 25% 以内；`docs/security/local-vault.md` 用的是 5090 的数（r2，PINR-14）。平均一半时间；N 张卡除以 N；租一张 GPU 每小时不到一美元 [estimate, unverified]。对照：主密码是用户自己的，50 位熵的
密码在同样条件下要几千年。也就是说：**开关打开后，配置文件副本的强度 = min(主密码, PIN)**，4 位 PIN 在一张显卡上几秒、6 位几分钟
（4、5 位两行是 2026-10-30 取消"至少 6 位"后补的，§17）。设置页的提示原话说的就是这一点；"5 次"只挡坐在电脑前的人，挡不住副本：
坐在电脑前的人不管 PIN 几位，仍然只有 5 次机会。

## 3. 锁屏解锁（`pin-restart-count.ts`，在锁屏自己的块里；`pin-restart-steps.ts unlock`，懒加载）

- **记录在不在、能给什么，搭在弹窗打开时已有的那次读取上。** `loadView` 的 `also` 本来就带 `sk_pin`、`sk_prf` 和设置，现在多带一个
  键 `sk_pin_restart`，读取次数不变（§8.3）。`openView` 只把这次读到的东西记在服务上（`ServiceCore.seen`，私有字段），别的什么都
  不算；锁屏（`Locked.tsx` 在弹窗的懒加载 `late` 块里，不计入弹窗体积）用 `restartOffer` 从这份读取结果算出记录的状态和 PIN 框
  （`restartState`，`pin-restart.ts`）。所以弹窗主块里**没有**记录的任何规则（§8.1）。
- **一个 PIN、两条路、一个计数。** 视图里有会话快速路径（`quick`）：走会话（`unlockWithPin`）；记录持有 wrap 时，每次都经
  `sessionTry`（见下）。视图里没有会话、而记录给出 PIN 框（重启之后）：直接加载懒加载块，走记录（`pin-restart-steps.ts unlock`）。
  会话答"ended"（看视图之后会话没了）且记录给出 PIN：也走记录。
- **先计数再派生（记录路径）。** 在库锁（`webLock("sixkey-vault")`）里重读同一条记录（按 id），fails + 1 **先写入**，然后在锁外做
  两次派生和解包、核对密钥 id。页面在派生中途被关：这次已经算过了。两个页面同时试：各花一次。没有剩余次数："exhausted"。
  第 5 次计数在**同一次写入**里把 wrap 设为 null（r2，PINR-07），派生用锁里读到的 wrap：第 5 次派生途中页面被关，磁盘上也不再有
  密钥材料（r1 要等派生结束才删）。派生之前还要求 wrap 的次数不少于现在新做一条会得到的次数（`restartIterations`，r2，PINR-02），
  否则答 ended、不计次（主密码记账随后按新次数重做）。
- **会话路径也在记录上先计数（`sessionTry`）。** 记录持有 wrap 时，会话路径的每次尝试在会话的 `unlockWithPin` **开始之前**，就在库锁里
  在记录上计一次（第 5 次同时拿掉记录的 wrap，不管这次输对没有）；然后才是会话自己的计数和派生。结果：输对 → 记录归零（第 5 次
  已拿掉的 wrap 不恢复，等主密码重做）；"ended"（会话已不在：什么都没派生，或 PIN 对了但布防刚好没了）→ 把这一次比对并交换地
  退回（锁屏随后走记录，记录自己再计一次）；输错 / 用尽 / 锁定 → 已计，不再动。笔误不计。所以"关掉弹窗 / 重启浏览器"不会给键盘
  前的人换来新的 5 次：两次主密码之间最多 5 次（service "a wrong PIN on the session counts on the record too …"、
  "a session that ended between the view and the try …"；crash "never fewer than the session spent, one more at most"）。
  这一步在锁屏的块里而不在服务里（服务的 `unlockWithPin` 与基线完全相同），源码规则保证页面上只有两个锁屏调用 `unlockWithPin`，
  并且在记录持有 wrap 时都经过 `sessionTry`（`pin-restart-source-rules`；变异体 Q4）。
- **输错。** 记 `pin_failed`；第 5 次：wrap 已随计数删掉（**密钥材料删除**，开关保留），记 `quick_ended`，答"exhausted"。
- **输对。** 在锁里比对并交换（同一 id、同一 wrap，fails 归零；第 5 次输对时 wrap 仍是 null，留待主密码重做，与会话路径相同）；
  这期间记录被结束、删除或重做 → "ended"，不开。然后和主密码
  解锁一样建立会话；派生期间有人锁定（lock epoch 变了）→ 作废，答"locked"。记录路径**不**为会话 PIN 布防（12 小时从主密码
  起算），下次锁定后仍走记录。
- **KDF 期间不阻塞。** PBKDF2 在 WebCrypto 里异步执行；锁屏转盘转动、`aria-busy`；e2e 在派生期间对页面做操作并得到响应（§9）。
- **主密码的记账**（`notePassword(s, kit, password)`，锁屏上主密码解锁后，懒加载，fire and forget）：稳定状态只读一次记录、不写
  （§8.3）。否则先**证明主密码**（r2，PINR-06）：用传进来的、刚才输入的主密码打开这个库的 VK（`openWithPassword`，与解锁同一函数），
  打不开就什么都不写——所以"主密码重置 14 天、恢复密钥不重置"是服务层自己的规则，不靠调用者：传恢复码、错的密码或不传都不变（r2
  测试）；两个锁屏的调用位置另有源码规则（只在主密码分支里、只在有记录时、各一处）。主体不合格的记录在这之前就删除（PINR-11，
  它不含库数据）。证明之后："暂停"的不动（留给设置页），但若它还带着 wrap（某个页面在密钥事件的收尾前死掉），顺手拿掉；其余（"pin"、
  "wait"：记录就是这把 VK 的）**先在 VK 下验 MAC，再写任何东西**（r3，PINR-R2-01）：验不过就比对后删除、到此为止（植入的记录，
  有没有 wrap 都一样，永远不会被续期）；验过之后 fails 归零；14 天重新计时（最多每天写一次，时钟倒退时立即写）；wrap 为 null、
  次数用尽、或次数低于现在的 `restartIterations` 时，用 sk_pin 的 pinKek 重做（新 id、新盐、`restartIterations`；PIN 几位都重做，
  2026-10-30 前这里要求 ≥6 位，§17）。
  写回时比对 id、wrap **和次数**（PINR-12：另一页面这期间记下的输错不会被它抹掉）。MAC 检查一次 HKDF 加 HMAC，约 1 ms，只在需要写的时候做。代价：需要写的那一次（最多每天一次，或第 5 次输错、"立即结束"之后）多一次主密码派生（2M 次）。

## 4. 设置页（`pin-restart-admin.ts`，只在设置页的懒加载块里）

> `enable`、`disable` 和开关已删（§18.2）；`genuineRestart`、`turnBackOn`、`setAsideRestart`、`removeRestart`、`makeRestart` 照旧。

- **只认 Sixkey 自己做的记录**（`genuineRestart`，r2，PINR-01）：完整（`restartOk`）、这个库、MAC 在它所写的 VK 下对得上（当前 VK，
  或被轮换下来的旧 VK——轮换暂停的记录是在旧 VK 下做的，`unwrapPreviousVks`）。其余（植入、损坏、别的库）在库锁里比对后删除，
  当作不存在。设置页的开关状态、PIN 框的状态行（库已解锁时）、"保存的内容"清单、重新开启、改 PIN 都经它。
- **开启**（`enable(password)`）：解锁、主密码保护、独享配置文件、PIN 已为这把密钥设置（几位都可以：2026-10-30 起不再要求 ≥6 位、
  不再有 `short_pin`，§17）；
  `verifyPassword` 核对主密码（错误照常记录）；用 sk_pin 的 pinKek 做记录（不需要再输 PIN），14 天从现在起算。
- **关闭**（`disable()`）：删除，不问密码。
- **重新开启**（`turnBackOn`）：记录必须是开着的（否则 `bad_state`：开启要主密码）。主密码：总可以。只输 PIN：只在"暂停"、并且
  **本页自己的密钥事件**（`rotated.ts rewrappedHere`）发生在 10 分钟内、针对的正是现在这把密钥和这组包装时；PIN 与 sk_pin 的
  pinKek 比对，错了记 `pin_failed` 并拒绝（UI 随即改要主密码），格式不对是笔误（`bad_pin`）。14 天从主密码起算（本页密钥事件的时间）。
  r2：只输 PIN 也按锁屏的规矩计数（PINR-10）：每次先在记录上计一次（库锁里、派生之前），计满 5 次就只能用主密码；输对则做出新记录、
  计数归零。"本页自己的密钥事件"只指本页**有人输入了秘密**的那几种（新/改主密码、重置、新恢复密钥、轮换、确认分片：`committed` 的
  `typed`），采用别处的新密钥（后台的一轮，或为别处的变更输入秘密）、加入、恢复不开这个窗口（PINR-09）。同步开着时，本页经同步
  引擎做的同样的变更也开（r3，PINR-R2-03：引擎的 `commitPublished` 带着刚输入的秘密，`KeyCommit` 的 `typed` 交给 `committed`；
  开同步前第 4(b) 步生成新恢复码同理），与所有者的原话"在设置里输一次 PIN 就能重新开启"一致；r2 把它们也关掉了（改过了头）。
  这一条参照 PRF 的 `rotated.ts`：Touch ID 在设置页换完密钥后按一下指纹即可，其他情况要主密码。见 §15 所有者事项 3。
- **改 PIN**（`PinAdmin.setPin`）：开关开着（= 有 Sixkey 自己做的、为当前 VK 做的、**可用的**记录：`genuineRestart`，记录的 vkId 是现在
  这把，且对改动前的 sk_pin `restartState` 答 "pin" 或 "wait"；r3 PINR-R2-04，r4 PINR-R3-01）时，新 PIN 只按普通 PIN 的规则检查（2026-10-30
  起，§17）；先删旧记录，再写新的
  sk_pin，再用新 PIN 重做记录（崩溃矩阵 §6）。植入的记录被删掉，新 PIN 不会因它得到记录（PINR-01）；**暂停的记录一律删除**、不重做（轮换
  暂停的、改主密码 / 重置 / 新恢复密钥暂停的，或关掉开关后被人写回的），没有 PIN 设置可对的记录（`restartState` 答 null）也一样；开关随之
  为关，再开启只能输主密码（已经没有记录可以"重新开启"：`turnBackOn` 答 `bad_state`；r4 后续，PINR-R4-01）。所以"换密钥或改主密码之后、重新开启之前改 PIN"不再自动恢复
  （维护者 2026-10-28 接受：收紧，且只在少见的流程里）。设置页 PIN 框原来的 6 位限制用的也是这个判断（`PinBox.tsx`：只在 `restart.state`
  为 "pin" 或 "wait" 时要求，PINR-R3-03）；2026-10-30 随规则一起删掉，PIN 框只看普通 PIN 的规则（§17）。
- 所有写入都在库锁里，并且只在当前密钥环（库、密钥、包装）和 sk_pin（盐）仍是记录所为的那一份时才写（`makeRestart`）。

## 6. 崩溃矩阵（`test/fault/pin-restart-crash.test.ts`，9 条）

每个操作在每一次写入的前后各"死"一次（新配置文件），然后一个健康的页面（需要时先模拟浏览器重启）检查：

- **"计数写了一半"**：死在计数写入前 → 什么都没试；写入后 → 这次算用掉了，但什么也没学到；记录的每次 `pin_failed` 都花掉一次；每次尝试最多花一次；还有次数时正确 PIN 照样能开。
- **"删除写了一半"**（第 5 次输错）：无论死在哪一点，记录都不会再被 PIN 打开，直到主密码重做——而主密码之后确实重做。
- 会话路径：记录在会话派生之前就计了数。
- 开启：记录要么完整（重启后能开），要么不存在。
- 改 PIN：新的 sk_pin 一旦落盘，旧 PIN 重启后永远打不开；新记录一旦落盘，新 PIN 能开；改没改成，看得出来。
- 移除 PIN、"立即结束快速解锁"：记录（或其 wrap）一旦没了，重启后什么 PIN 都打不开；r2 加了一条：已经硬锁定（会话没了）的那些点上，
  wrap 一定已经拿掉（先拿 wrap 后锁定，审查 R20）。
- 密钥变更：新密钥环一旦落盘，无论 wrap 拿掉没有，记录都不会再打开。

## 12. 偏离与原因

1. **KDF 是 PBKDF2，不是 Argon2id。** brief 写"Argon2id"，但本机主密码用的就是 PBKDF2-SHA256（2M），仓库里没有 Argon2：WebCrypto
   没有，wasm 被 PLAN §5.1 否决，且需要改 `check-dist` 强制的 CSP。按"与主密码同一 KDF、参数不弱"实现：PBKDF2，每次猜测 ≥2.6M 次。
   以后 WebCrypto 原生支持 Argon2id 时，主密码和这条记录应一起换（§15 所有者事项 1）。
2. **第 5 次输错、"立即结束快速解锁"：删除的是记录里的密钥材料（wrap → null），不是整条记录。** 所有者原话"输错 5 次，这份保存在
   电脑上的 PIN 记录就被删掉，之后只能用主密码，和现在一样"。磁盘上已经没有任何能被 PIN 打开的东西，之后只能用主密码——这两点
   完全满足；保留的空壳（id、库、时间、MAC，无密钥材料）只用来记住"开关是开着的"，让下次主密码自动恢复，就像现在会话 PIN 在下次
   主密码后自动重新生效（"和现在一样"）。所有者 2026-10-30 按推荐定为保持这样（20 号文件补充问题 1 (a)；§15 所有者事项 2）。
3. **暂停后"在设置里输一次 PIN 就能重新开启"：只在本页刚换完密钥的 10 分钟内。** 其他情况（另一个页面换的、从同步来的、超过 10 分钟）
   要主密码。这照搬 Touch ID（`rotated.ts`，OWNER-DECISIONS/17 Q3 的"一次触碰"同样只在刚换完时），brief 也要求参考它。最常见的情况
   ——在设置页改完主密码顺手重新开启——就是输一次 PIN。所有者 2026-10-30 按推荐定为保持这样（20 号文件补充问题 2 (a)；§15
   所有者事项 3）。
4. **开启不进安全记录。** 开、关不写安全记录（`pin_set` 等现有条目不变；输错、第 5 次照常记 `pin_failed`、`quick_ended`）：
   新增一种记录类型要新文字，保险库页面没有余量（§8.2）。§15 所有者事项 4。（2026-10-29 已定，按推荐：20 号文件补充问题 3 (a)；
   预算整理 3 已实现：开启和关闭记 `pin_restart_on` / `pin_restart_off`，输错、第 5 次仍照常记 `pin_failed`、`quick_ended`，
   什么时候记见 BUDGET3-NOTES.md §5.2。）

## 13. 残余风险

- **离线猜 PIN**（所有者接受的代价，§2.4；所有者 2026-10-28 的补充：已告知约 5 分钟、8 小时，"风险由用户承担"；2026-10-30 取消"至少 6 位"，
  §17）：4 位 PIN 在一张显卡上几秒，6 位几分钟。坐在电脑前的人仍然只有 5 次机会。
- **"删除"之后数据库文件里的旧字节**（r2，PINR-04）：关掉开关、第 5 次输错、换密钥之后，`chrome.storage.local` 的 API 里确实已经
  没有旧记录（审查 P4、E5 证实），但 LevelDB 在整理文件之前可能还留着旧字节；这之间拿到的配置文件副本仍可被离线猜 PIN。PRIVACY.md、
  local-vault.md 已如实写明。换密钥**只保护之后新加的账户**：那份副本旁边很可能还有同一把旧 VK 加密的保险库（LevelDB 里旧槽的残留，
  与 Phase 0 那一行同理），TOTP 密钥本身也不随换密钥改变；已有账户要让旧副本失效，只能到各网站重新签发 2FA（r3，PINR-R2-02；r2 写的
  "换一次密钥就能让旧副本无用"不成立）。设置页没有加字（文字预算，§8.2）。
- **能写存储的人**可以回滚次数、整条记录回滚、挪 14 天、植入记录（§2.3 第 4–6 条）；这些都不比"直接复制离线猜"更强。
- **会话计数与记录计数之间崩溃**：会话路径先在记录上计一次，再在会话上花一次；死在两者之间，记录多计一次（那次尝试什么也没派生）：
  只少一次机会，不多。
- **会话路径的记录计数在锁屏里，不在服务里**（§3、§8.1：为了不进弹窗的计数体积）。服务的 `unlockWithPin` 本身不碰记录：将来若有
  别的页面直接调用它，记录持有 wrap 时那里的尝试就不在记录上计数。源码规则把调用者限定为两个锁屏，并要求它们经 `sessionTry`
  （`pin-restart-source-rules`），新的调用者会让这条测试失败。
- **侧边栏体积测试只剩 12 B**（§8.1、§16.1）：不是本功能的预算，但下一个往弹窗 / 侧边栏静态部分加代码的改动会先撞上它。
- **密钥事件收尾前页面死掉**：新密钥环已落盘、旧 wrap（旧 VK，在 PIN 之下）还在磁盘上，直到下一次密钥事件收尾或主密码记账把它拿掉；
  这期间它永远不会被提供或打开（`restartState` 答"paused"）。离线猜中 PIN 的人能拿到**旧** VK。
- **派生期间另一个页面换了密钥**：与 PRF-NOTES 的 S4 同一个已知限制（与主密码解锁相同）：会话里写进旧密钥，它什么也打不开、写不了，
  直到下次锁定；记录路径的比对交换会在收尾已拿掉 wrap 时拒绝。
- **`wraps` 字段是密钥环各包装的密文**（`wrapsTag`：只有 48 字节的 AES-GCM 密文，没有 IV、没有 KDF 盐，sk_quick 在内存里存的是同一个
  标签）。改主密码后，暂停的记录里还留着旧密码包装的密文，直到重新开启；没有旧的 IV 和盐（随清理一起消失）它打不开任何东西，
  而能从数据库残留字节里找回旧 IV 和盐的人，也能在同一处找回旧密文本身（local-vault.md "Limits"），所以它不增加暴露。若审查人
  认为仍应避免，可改存其 SHA-256（`restartState` 需改为异步），见 §14 第 9 条。
- **JavaScript 不能可靠清零内存**：pinKek、KEK 用完 `fill(0)`，但不保证。

## 17. PIN4：取消"至少 6 位"（所有者 2026-10-30 的决定）

**决定。** 所有者 2026-10-30（`OWNER-DECISIONS/20-unlock-after-restart.md` 的"补充（2026-10-30）"），原话："太复杂了 我设置4位 pin
你都拦我 搞得比 Windows 和 macOS 的系统级密码还麻烦,别人 macos 我设置4位数字登入都可以 你现在纯纯是用自我设限的形式给用户加固"。
"重启后也可以"不再单独限长：PIN 的规则和普通 PIN 完全一样，就是现有的 `checkPinPolicy`（4 到 8 位数字，弱 PIN 照普通规则拒绝）。
它取代 20 号文件第 2 节"PIN 长度"和 2026-10-28 补充里"至少 6 位"的说法，也取代本文原来的 6 位规则（§1、§3、§4、§5 已改准，
历史记录 §10、§16 里的 N14、N15、A9、R30、Z14、PB1、PB2、K3、K7 守的是那条已删的规则，保留原样作为历史）。

**理由，照实。** 6 位的下限挡不住离线猜测：拿到这个浏览器配置文件副本的人，用一张高端显卡试完所有 6 位 PIN 约 5 分钟、8 位约
8 小时（§2.4），所以 4 位只要几秒（约 3 秒；5 位约 29 秒）。对拿到副本的人，6 位和 4 位都是"很快"；对每天用的人，6 位的下限
却是一道门槛（4 位 PIN 时开关是灰的，要先改 PIN）。代价照旧如实告知、只提示不拦：设置页开关下面的 `rsCost`"拿到这个浏览器配置文件
副本的人可以离线猜你的 PIN；PIN 越长越难猜。"原样保留，量级写在本文 §2.4、`docs/security/local-vault.md` 和 PRIVACY.md。**坐在电脑前
的人仍然只有 5 次机会**，不管 PIN 几位：每次尝试先在记录上计数再派生，第 5 次输错就拿掉记录里的密钥材料（§3），这条不变。

## 18. PINONE：PIN 一直能用，唯一的限制是连续输错 5 次（所有者 2026-10-30 第二条决定）

**决定。** `OWNER-DECISIONS/20-unlock-after-restart.md` 的"补充（2026-10-30，第二条）"。所有者先说"最多就是加一个 pin 码重试错误的限制"；
维护者问另外两条时间限制要不要一起去掉，所有者选了"只留输错 5 次（推荐）"。于是：

- 设了 PIN，它就一直能用，浏览器重启、扩展重新加载（包括商店更新）之后也能用。"重启后也可以"这个开关整个去掉。
- 去掉普通 PIN 的"到浏览器关闭为止、最多 12 小时"，也去掉"每 14 天输一次主密码"。
- 唯一的限制：**连续**输错 5 次，就要输一次主密码；次数记在磁盘上的记录里，重启、重新加载都不清零；输对一次就清零。
- PIN 规则 4 到 8 位数字；弱 PIN（重复、连号、常见）只提示（`pinWeak`），不拒绝（维护者按"只提示、不拦"定）。
- 设 PIN 的地方如实说代价（`rsCost` 挪到设 PIN 的表单上方）。
- 不变：换密钥或改主密码后记录暂停（本页 10 分钟内只输 PIN 重新确认，否则下次输主密码自动恢复）；"共享或由脚本控制"没有 PIN；
  "每次关闭弹窗时锁定"照样用 PIN 重新打开；Touch ID 的 14 天不动。

它取代 §1–§17 里讲开关、12 小时、到浏览器关闭为止、14 天、弱 PIN 拒绝的说法（那些节保留原样作为历史，文件开头和 §1、§4、§5 已注明）。
**离线代价照实：** 拿到这个浏览器配置文件副本的人，用一张高端显卡大约 3 秒试完所有 4 位 PIN（RTX 5090 约 2.3 秒），6 位约 5 分钟，
8 位约 8 小时（§2.4）；坐在电脑前的人只有连续 5 次机会。以前这个代价只在打开开关的人身上，现在每个设了 PIN 的人都承担。

  原样；写入之间的窗口只剩几次存储写入（e2e 里实测过：原来"先写 `sk_pin` 再派生"时，设完马上关页面会让新 PIN 等主密码）。

### 18.3 主密码记账与两种迁移

`notePassword`（锁屏用主密码解锁之后，弹窗、侧边栏、设置页解锁栏都调；恢复密钥解锁不调）。r2 起（§18.13 PO-02）：

0. **证明**是服务自己的一次性标记：`unlockWithPassword` 成功时在同一个服务实例里记下 VK 的 id 和这次会话的锁定计数（ServiceCore
   `typed`）；恢复密钥、门禁、PIN、失败的尝试、别的页面都不设；任何锁定之后作废（锁定计数），被记账取走一次就没了。没有标记什么都不读、
   不写（PINR-06 照旧：恢复密钥、错的或没有的主密码什么都不改）。r1 是把输入的主密码再派生一次来证明，现在省掉了这一次。
1. 一次 `loadView`（记录、`sk_pin`、设置随指针那次读来）；`restartState` 为 null（共享、或这些密钥下没设 PIN）→ 什么都不做。
2. **稳定状态**：状态是"pin"、记录完整（`restartOk`）、没有计过错、wrap 的次数不低于现在新做的（`restartIterations`）、并且 MAC 在
   会话里的 VK 下对得上（`sessionVk`，用已经读到的设置，不派生）→ 什么都不写。所以平常每次输主密码不会改写记录。
3. 否则（没有记录、wrap 被拿掉、计过错、暂停、次数太低、MAC 不对或根本不完整）：用会话里的 VK 打开 `sk_pin` 里的 pinKek，做一份新记录
   （新 id、新盐、新 MAC、不计次数；**一次** 2M 派生），在库锁里比对读到的原样后写入（读后被别的页面改过就不写）。
4. `sk_pin` 形状完好、但会话里的 VK 打不开它的密文（损坏）：永远做不出记录，于是在库锁里比对后把它和旁边的记录一起删掉（先记录后
   `sk_pin`，和移除 PIN 的顺序一样）；设置页随即显示没有 PIN，可以重新设（§18.13 PO-04）。
5. **锁屏等它做完再显示列表**（`Locked.tsx`、`UnlockBar.tsx`：`await`，最多 10 秒，之后照样显示列表、让它在后台继续；出错照旧吞掉）。
   等的时候界面仍是"正在解锁"，没有新文字。稳定状态只多几次读取；需要重做记录的那一次多一次 PIN 派生的时间（e2e 实测：要做记录的那次 791 ms、稳定状态 184 ms，见 §18.7、§18.13）。
   这样弹窗一出列表就被关掉，记录也已经做好（r1 不等，弹窗马上关就白做，审查探针 B 复现过）。

两种迁移都走这条路，不需要单独的迁移代码：

- **开过开关的记录**：格式没变，原样就能用（"pin"）；14 天的判断删了，`lastPasswordAt` 再旧也照用。测试
  "a record made with the old switch, its master password 30 days old: used as it is"。
- **只设过会话 PIN 的人**（有 `sk_pin`、没有记录）：更新本身会重新加载扩展、清空会话内存，所以没有要迁移的会话状态。锁屏读到"有 PIN
  设置、没有记录"→"wait"：主密码框和 `lockPinWaiting` 那一行；输一次主密码，第 3 步就做出记录，之后 PIN 一直能用，**不用重新设 PIN**。
  测试"a PIN set before its record was its one way (sk_pin, no record): waits for the master password once, then works, also after a restart"。

### 18.7 行为上的变化与残余风险（照实）

- **离线代价落到每个设了 PIN 的人身上**（上面"离线代价照实"）。只设过会话 PIN 的人，更新后第一次输主密码就会在磁盘上得到这份记录，
  他们没有在那一刻看到代价提示（提示在设 PIN 的地方和"保存的内容"里一直有）。这是维护者定的迁移；要不要在迁移时另外告知，交维护者。
- **恢复密钥解锁不再让 PIN 恢复。** 原来会话 PIN 由任何一次解锁（包括恢复密钥）重新武装；现在只有主密码会重做记录（PINR-06 的规则
  从记录推广到唯一的 PIN）。恢复密钥本来就只用来找回，影响很小。
- **改变锁定方式不再结束 PIN**（记录在磁盘上）；门禁的武装照旧结束。
- **每次 PIN 解锁都要派生约 2.6M 次 PBKDF2**（原来会话 PIN 只要 600k）：这台 Mac 上 Playwright 的 Chromium 约 0.3 秒（e2e 实测 "每次关闭弹窗时锁定" 三次：298、286、290 ms）；慢电脑预计 2–4 秒，
  派生在 WebCrypto 里异步，页面不卡（e2e 测过）。"每次关闭弹窗时锁定"模式下每次打开弹窗都要派生一次。
- **需要重做记录的那次主密码解锁慢一次 PIN 派生**（迁移后的第一次、连错 5 次后、"立即结束快速解锁"后、换密钥后）：锁屏等记账做完
  才显示列表（r2，§18.3 第 5 步），这台 Mac 上多 约 0.6 秒（e2e 实测：从按回车到列表出现，要做记录的那次 791 ms，稳定状态的一次 184 ms），慢电脑预计 1–3 秒；平常的稳定状态不派生。最多等 10 秒，超过就先显示列表、
  记账在后台继续，那时弹窗若被关掉，记录就要等下一次主密码。
- **`sk_pin` 损坏**分两种（r2，§18.13 PO-04）：形状坏了（读不出）时锁屏什么都不显示，设置页按"没有 PIN"处理，可以重新设；形状完好、
  密文坏了时锁屏显示"输一次主密码后，PIN 就能重新使用。"，下一次主密码就把它（连同旁边的记录）删掉，之后锁屏不再有那一行，设置页显示
  没有 PIN、可以重新设。只在 `sk_pin` 的 AES-GCM 认证在会话的 VK 下失败时才删；派生密钥出错、WebCrypto 别的错误一律不删、原样留着
  （§18.14 S-02）。这次删除不记安全记录：很少发生，设置页随即显示没有 PIN、可以重新设（维护者定，§18.14 S-05）。
- **"每次关闭弹窗时锁定"下，派生途中关掉弹窗会花掉一次**（先计数后派生，§3）：这个模式下每次打开都要派生，比以前更常见；连续 5 次这样
  就要输一次主密码。
- **门禁在存储一时读不出时不再被丢掉**（`device-unlock.ts`）：原来只有门禁（没有 PIN）时会丢掉武装，和 PIN 并存时不丢；现在门禁总是单独
  一份，统一按原测试的说法"一时读不出存储不是武装的错"处理，留着（它仍受 12 小时和时钟检查约束）。
- LevelDB 旧字节、能写配置文件存储的人回滚计数或塞回旧记录（§2.3）：照旧，见 `docs/security/local-vault.md` Limits；"挪动 14 天"那一条没有了。
