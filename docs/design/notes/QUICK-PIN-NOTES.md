>
> **2026-10-30 补记（OWNER-DECISIONS/20 第二条补充，`PIN-RESTART-NOTES.md` §18）：本文的会话 PIN 已被取代。** PIN 不再存在会话内存里
> （`sk_quick` 下用 PIN 包住的 VK 不再做），每个 PIN 都只用它在磁盘上的记录 `sk_pin_restart`：浏览器重启、扩展重新加载之后也能用，
> 没有 12 小时、到浏览器关闭为止和 14 天这些限制，唯一的限制是连续输错 5 次（计数在记录上，重启不清零）；弱 PIN 只提示、不拒绝；

> 本文讲 12 小时、会话 PIN、弱 PIN 拒绝（`weak_pin`）的地方保留原样作为历史。

`docs/design/proposals/QUICK-UNLOCK.md`（2026-10-19 获批）把会话 PIN 和快速锁定放在最前，这是所有者定下的优先级：“PIN 是最基础的功能：想快速使用 TOTP 扩展的人，用 PIN 快速解锁，再快速上锁。”本包实现这一阶段：按 §5 设计的 §4.6 方案 F（`sk_pin`、`sk_quick`、PIN 解锁、普通上锁与硬上锁、PIN 策略、5 次尝试、12 小时），以及 §5.12（立即锁定、后台脚本(service worker)中的 `lock` 命令、已打开的页面响应锁定纪元、弹窗关闭时上锁、`profile` 标记）。设备解锁（PRF、Touch ID / Windows Hello 开关、第 2 阶段）不在本阶段，本阶段的文案中也没有任何地方提到 Touch ID 或 Windows Hello。`QUICK-UNLOCK.md` 本身未改动；本包与它不一致、或发现缺口之处，见 §9，并附所采取的处理方案。

## 1. PIN 实际是什么（按已构建的实现）

- **存放位置。** `sk_pin`（chrome.storage.local）是设置记录：`pinKek = PBKDF2-SHA256(NFKC(PIN), 16-byte salt,
600k)`，用 AES-GCM 封装，密钥为 `HKDF(VK, ∅, "sixkey/v1/pin-cfg")`，AAD 为 `sixkey-pin|1|{vaultId}|{vkId}`，另附 PBKDF2 参数和 PIN 的长度。`sk_quick`（仅 chrome.storage.session）是用 `pinKek` 封装的保险库密钥，AAD 为 `sixkey-quick|1|{vaultId}|{vkId}|{armedAt}|{expiresAt}`，并带有尝试次数计数器。`src/core/crypto/pin.ts` 含这两种记录；`src/core/service/pin-store.ts` 是 `sk_pin` 的唯一写入方；`src/platform/session.ts` 是唯一写出 `sk_quick` 这个名字的文件，并且只把它交给 session 存储区。
- **配置(profile)的副本能拿到什么：** `sk_pin`；没有保险库密钥，它什么也打不开（拿到保险库密钥的人可以暴力破解 PIN，所以设置框里提醒不要复用 PIN）。磁盘上没有任何东西能凭 PIN 打开保险库。
- **何时能凭它打开 Sixkey**（以下全部条件，每次使用时都检查：锁屏、PIN 解锁、设置框）：单人配置(solo profile)；未过 `expiresAt`（`now = expiresAt` 仍算有效）；时钟落后 `armedAt` 不超过 60 秒；还剩尝试次数；保险库 id 与保险库密钥是该记录当初布防时对应的；密钥环的封装（wraps）是它布防时所处的那一组（第 2 版，`wrapsTag`：任何重新封装都会使其失效）；并且 `sk_pin` 仍是它当初布防所依据的那份设置（同一保险库、同一密钥、同一 PBKDF2 盐：`sameSetup`）。
- **布防。** 单人配置中，每一次主密码解锁和恢复密钥解锁都会写入 `sk_quick`（自当前起 12 小时，5 次尝试），无论哪种锁定模式；设置 PIN 时也会布防（刚刚输入过主密码）。PIN 解锁从不重新布防：12 小时从根密钥（root secret）起算。`verifyPassword`（H3 导出校验、每一次同步 `pw_auth`）未改动，也从不接受 PIN。
- **PIN 解锁**（`VaultService.unlockWithPin`），按顺序：锁定纪元；设置（视图需要它们；配置必须是单人配置）；在 `webLock("sixkey-quick")` 内读取记录，并且在**任何**派生之前先扣掉一次尝试并写入；`loadView` 在其第一次读取中带上 `sk_pin`（校验保险库、密钥和设置）；PBKDF2 与解封；错误：记录 `pin_failed`，若这是最后一次尝试，则删除 `sk_quick` 并记录 `quick_ended`；正确：在快速锁内通过比较并设置（compare-and-set）把计数器恢复为 5（其间发生的硬上锁或新的布防绝不会被覆盖），然后走与密码解锁相同的 `finishUnlock`，使用开始时读到的纪元。如果期间有锁定发生，新会话会被清除，回答为“已锁定”。格式错误的 PIN（NFKC 之后不是 4 到 8 位数字）按输入失误处理：不扣尝试，不写记录。
- **策略**（`src/core/crypto/pin-policy.ts`，仅设置页面使用）：NFKC 并去除首尾空白后，4 到 8 位 ASCII 数字；拒绝：由更短片段重复而成的（全部数字相同、1212、123123）、正反两个方向的连续序列且 9 与 0 相接（1234、7890、987654），以及一小份常见 PIN 列表（1004、2000、2580、112233、159753、5201314 …）。设置框除设计文案外不作其他推荐；文案示例中默认为 6 位数字。

## 3. 快速锁定（§5.12）

- **立即锁定**：沿用顶栏上现有的按钮，现在带有 `id="lock-now"`，执行普通上锁，然后显示锁屏，焦点落在 PIN 输入框。其提示文字写明了快捷键（“锁定 (Alt+Shift+L)”），并且在 Chrome 的快捷键字符串格式合适时带有 `aria-keyshortcuts`。
- **快捷键**：manifest 命令 `lock`，建议键 `Alt+Shift+L`，描述为 `__MSG_cmdLock__`（“锁定 Sixkey”）；无需权限。在 `sw.ts` 顶层处理（`chrome.commands.onCommand` → `service.lock()`），因此没有任何页面打开、后台脚本(service worker)休眠之后也能工作。设置 › 安全 › 安全模式显示当前绑定的按键（`chrome.commands.getAll()`，外观设置已在使用），并可打开 `chrome://extensions/shortcuts` 去修改。冲突检查：在 Windows、macOS、Linux 上，Chrome 的默认快捷键都不使用 Alt+Shift+L [根据 Chrome 公布的快捷键列表推断，未重新测试]；在 ChromeOS 上，Alt+Shift+L 是系统快捷键（聚焦启动器）[未验证]，在那里系统优先，用户可以另选按键；在 macOS 上，快捷键绑定后，Option+Shift+L 在页面中会输入“Ò”，这与 Alt+Shift+K 已有的取舍相同。如果另一个扩展已占用某个建议键，Chrome 不会再把它分配出去。
- **弹窗关闭时上锁**即现有的“每次弹窗关闭时”锁定模式（`autoLock.mode: "always"`），复用而不重复实现：密钥像以前一样只存在于弹窗的内存中；变化在于，单人配置下主密码同时会布防 `sk_quick`，所以下一次弹窗打开时显示的是 PIN。PIN 设置框会说明在哪里选择它。
- **`profile` 标记**：`Settings.profile: "solo" | "shared"`（`types.ts profileOf`）。由首次运行时的提问和安全模式的两张卡片（`applyPreset`）设置；属于 `detectPreset` 的一部分（带有共享卡片设置的单人配置显示为“自定义”，绝不显示为“共享”）；调用方省略它时由 `updateSettings` 保持原值；在它出现之前保存的记录，只有设置与共享预设完全一致时才读作 “shared”。“Shared”拒绝布防、设置 PIN 和 PIN 解锁，`RoutedSession.get()` 会清除它在那里发现的任何 `sk_quick`。

## 4. 页面

- **弹窗锁屏**（`Locked.tsx`）：有可用 PIN 时直接打开在 PIN 上，在第一帧之前就已决定（来自 `openView`），因此按下 Alt+Shift+K 后紧接着输入的数字会落进 PIN 输入框。只有一个 `<input type="password"
inputmode="numeric" autocomplete="off">`，带可见标签，剩余尝试次数那一行通过 `aria-describedby` 关联，错误放在 `role="alert"` 中。按 Enter 提交，输入长度达到 PIN 的长度时自动提交。“使用主密码”只隔一个按钮；第 5 次输错 PIN 或到期之后，会切换到那里，带焦点并说明原因。
- **允许粘贴。** NIST SP 800-63B §5.1.1.2 要求验证方允许粘贴；禁止粘贴会破坏密码管理器和辅助工具，却挡不住任何攻击者（拿到 PIN 的人本来就能输入）。取值会去除首尾空白并做 NFKC 规范化。
- **不留痕迹**：PIN 一提交，输入框就被清空，早于得到答复；PIN 只交给服务，别无去处（不进 URL，不进日志；出错只记录其错误码）。一项单元测试遍历所有路径，在 chrome.storage.local、诊断信息和安全记录中都找不到 PIN、保险库密钥或 `sk_quick`。
- **设置 › 安全 › PIN 快速解锁**（`PinBox.tsx`，位于安全模式之前）：说明 PIN 的用途及它拦不住什么（`pinHonest`）、当前状态（“已开启（6 位）。它可打开 Sixkey，直到 18:31。” / “在你下次输入主密码后恢复可用”）、设置 / 更改 / 移除（每一项都要再次输入主密码）、立即结束快速解锁（无需密码：它只是取消一条入口）。已锁定时只显示状态；在共享配置中，则说明为何没有 PIN。
- **设置页面的解锁栏**在有可用 PIN 时也接受 PIN，主密码只隔一个按钮（§5.10）。
- **失败尝试通知**把 `pin_failed` 与错误密码、错误恢复密钥一起计数（`FAILURES`），其文字现在也这样说明。PIN 解锁之后它会显示，但**不会确认清除**：安全日志的规则是，只有刚刚输入过主密码的人才能把计数清下去，而 PIN 的证明力比这弱。它会在下一次主密码解锁时消失。

## 5. 崩溃矩阵（test/fault/quick-pin-crash.test.ts）

对 chrome.storage.local 或 chrome.storage.session 的每一次写入，都是页面可能死亡的点位：写入落地之前，或刚刚落地之后；之后由同一存储上的一个健康页面做检查：

| 操作（写入顺序）                                                                                     | 每个点位都必须成立的条件                                                                                                        |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 设置 PIN：`sk_quick` 清除 → `sk_pin` 写入（保险库锁内，仅在当前密钥下）→ `sk_quick` 布防 → `pin_set` | 除新 PIN 外，任何 PIN 都不可能有效；新 PIN 仅在 `sk_pin` 已存入后才有效；下一次输入主密码之后，恰好就是已存入的那份设置         |
| 更改 PIN（顺序相同）                                                                                 | 旧 PIN 从第一次写入起就失效，并且在下一次输入主密码之前不会恢复；之后只有已存入的设置有效（更改要么明确发生了，要么明确没发生） |
| 移除：`sk_quick` 清除 → `sk_pin` 移除 → `pin_removed`                                                | `sk_pin` 一旦消失，不论现在还是下一次输入主密码之后，都没有 PIN 可用；如果它还在，设置框显示 PIN 为开启                         |
| 输错 PIN：写入扣除的尝试 → … → `pin_failed`                                                          | 已记录的错误 PIN 一定扣过一次尝试；每次尝试至多扣一次；正确的 PIN 仍然有效                                                      |
| 第 5 次输错 PIN：… → `sk_quick` 删除 → `quick_ended`                                                 | 即使删除丢失，在输入主密码之前 PIN 也绝不会再次生效，并且下一次查看会删除该记录                                                 |
| 12 小时闹钟：`sk_quick` 删除                                                                         | 即使删除丢失，过了 `expiresAt` PIN 也绝不会生效                                                                                 |

`sameSetup` 使前三项在两次写入的任意顺序下都成立，所以仅靠这个矩阵分不出顺序的先后（顺序变异体 M48 和 M49 都在它面前存活）。顺序仍然保留，使每一次单独的写入都已经朝安全状态迈进；同一文件中另有两项测试通过记录写入顺序把它钉住。

## 6. 预算与读取（已实测；第 1 版，第 2 版见 §10.2）

- **弹窗 gzip**（`node scripts/check-dist.mjs`，生产构建）：**58.4 KB**（59,812 B），预算 60 KB（61,440 B）；此前为 55.3 KB（56,674 B）：静态部分 54.3 KB（原 51.4）+ zh_CN 弹窗词条目录 4.1 KB（4,162 B；原 3,992）。预算未上调。为了保持在预算内，从弹窗中移出的内容有：PIN 策略（`pin-policy.ts`）和 PIN 设置框的操作（`pin-admin.ts`，设置/更改/移除/状态/结束），它们只由设置页面引入；一项测试保证它们不进入弹窗的依赖图。我们还构建并测量了 PIN 解锁的懒加载分块：它反而让弹窗**更大**（静态部分 54.7–54.8 KB），因为打包器随后会把该分块与弹窗共用的模块拆成另一个独立分块；已放弃。
- **同步发布开关打开时**（在临时副本中把 `SYNC_UI_IN_STORE_BUILD = true` 后的同一构建，已测量，未发布）：**61,394 B**，比 61,440 B 的预算少 46 B（原为 58,476 B）。能通过，但已无余量。见“所有者问题”第 1 项。
- **完整词条目录**：zh_CN **11,881 B**，`FULL_CATALOG_GZ` 为 12,288 B（原 11,126），en 为 10,486 B（原 9,819）。新增的设置文案放得下，所以没有构建拆分的词条目录；还剩 407 B 余量。
- **读取**（`test/unit/quick-read-budget.test.ts`，弹窗的真实接线）：有可用 PIN 的锁屏读取 chrome.storage.local 3 次（预算 4），`sk_pin` 包含在指针的第一次 get 中；锁屏 + PIN 解锁：**7** 次 local 读取，与锁屏 + 密码解锁（7）相同，另有 6 次 session 读取（密码为 3）。未设置 PIN 时，密码解锁与以前一样做 7 次 get，其中一次也会请求 `sk_pin`（键不存在：没有字节）。降级镜像开关（10）未变。

### 7a. 变异体

## 8. 与同步的交互（SYNC-DESIGN 第 26 版 §6、§7）

- 普通上锁也是上锁：它推进纪元，所以每个打开的同步流程都会结束（§6，第 24 版）；PIN 解锁绝不会恢复任何同步流程。
- PIN 打不开任何由主密码关卡保护的东西：每一个 `pw_auth` 操作都要求在该流程中输入主密码，而 `verifyPassword` 不接受别的（代码未改动，并有一项测试）。
- `sk_pin` 是每台设备独有的，绝不同步、镜像、备份或导出；关闭同步时会保留它（`LOCAL_ONLY_KEYS`，不在 `SYNC_OFF_KEYS` 中）；它不是保险库数据（`hasAnyData`）。每一次被采纳或提交的密钥变更都会结束会话层（`committed()`），清理步骤会把 `sk_pin` 迁移到新密钥。

## 9. 与 QUICK-UNLOCK.md 的偏离，以及发现的缺口

1. **安全日志版本。** §5.10 要求“两个功能共用一次版本号提升”。自 M6 起，代码的规则是新增种类不需要提升版本，因为每个版本在重写记录时都会保留它不认识的种类的条目（提升版本会让旧版本完全停止记录）。四个种类（`pin_set`、`pin_removed`、`pin_failed`、`quick_ended`）加入 v2，不提升版本。处理：遵循代码；设计中的那句话早于 M6。
2. **`sk_quick` 携带 `kdf`**（`sk_pin` 的 PBKDF2 参数的副本，包括盐）。§5.2 的 `QuickSession` 没有列出它。这样在派生之前可以省去一次对 `sk_pin` 的读取，而它的盐指明了该记录是依据哪份设置布防的，`sameSetup` 会检查这一点。`armedAt`/`expiresAt` 仍按设计由 AAD 绑定。
3. **“弹窗关闭时上锁”**就是现有的“每次弹窗关闭时”模式，不是新选项（§5.12 第 4 项读起来像新选项；任务说明要求复用）。§5.4 的“非 ‘always’ 模式”、§7.1 的“‘always’ 模式拒绝布防和设置 PIN”以及 §7.3 第 5 项，被理解为已被 §5.1 第 5 项的 profile 规则（2026-10-19 修订）取代；测试和变异体针对的是 profile 规则。
4. **密钥变更时的硬上锁**比 §5.5 的列表更宽：每一个已记录的密钥事件和保险库密钥的每一次变更（因此也包括新恢复密钥、`sync_on`，以及从另一台设备采纳、保险库密钥相同的密码变更）。任务说明要求“主密码变更”为硬上锁；§5.9 只说那时设备解锁仍然可用。处理：采用硬上锁，偏保守；下一次输入主密码会重新布防。首次上传前的密钥环时间截断（种类 `null`，密钥相同）不算硬上锁。
5. **密钥变更时的 `sk_pin`** 会在新密钥下重新加密（§5.9 的第一个选项），而不是丢弃。任何持有的密钥都打不开的、已损坏的、或属于另一个保险库的，会被移除（它不含保险库数据）。
6. **PIN 的操作并非全是服务方法**（§5.10 把 `setPin`、`removePin`、`quickState` 列在服务上）：为了不让它们进入弹窗的包，它们放在 `PinAdmin`（`pin-admin.ts`）中，通过元素访问复用服务自己的步骤，这是 `sync-flows.ts` 开创的模式；允许这种访问的源码规则现在同时列出这两个文件。`unlockWithPin`、布防以及锁屏的查看仍是服务自己的。
7. **`loadView(also)`**：§5.10 中指针读取上可选的“also read”已实现（仅用于 `sk_pin`），所以锁屏和两种解锁都不会为 PIN 多读任何东西。
8. **“已锁定”的答复**：§5.4 说派生期间发生的上锁会使新会话作废；服务也会如实报告，所以锁屏会显示“Sixkey 刚刚已锁定。请重新输入 PIN。”，而不是显示已经作废的验证码。
9. **立即锁定的“可见标签”**（§5.12 第 1 项）：弹窗顶栏在语言切换和设置旁边没有放文字标签的空间；按钮保留图标、一个无障碍名称（“锁定”）和带快捷键的提示文字。
10. **立即结束快速解锁**不要求主密码（§6.3：“每项更改都要求主密码”）：结束只是取消一条入口，与立即锁定类似。
11. **PIN 解锁之后的通知**会显示，但不确认清除（见上文 §4）。设计中对此没有说明。
12. **文案**：设计中的 `quickLead`、`quickSharedOff` 和 `quickNeedsPassword` 提到了 Touch ID 和 Windows Hello，而本阶段并没有这些；本阶段的文字（`scripts/i18n/quick.py`）只说当前属实的内容。第 2 阶段会加入它自己的文案。
13. **缺口：`local-vault.md`、`PRIVACY.md`、`ARCHITECTURE.md`**（§10“仍待办”）此处未编辑；建议文本如下：
    - local-vault.md，“受保护的内容”：“PIN（会话快速解锁）：可以挡住坐在这台电脑前的人，5 次尝试；挡不住这台电脑上的程序，也挡不住使用浏览器开发者工具的人；浏览器重启时结束，并在输入主密码 12 小时后结束。磁盘上没有任何东西能凭它打开保险库。”“上锁”：“立即锁定、Alt+Shift+L 快捷键、空闲计时器和屏幕锁定都是普通上锁（可用的 PIN 能重新打开 Sixkey）；第 5 次输错 PIN、立即结束快速解锁、锁定模式变更、共享配置、任何密钥变更以及浏览器重启都是硬上锁。”“权限”：“锁定快捷键是 manifest 命令，不需要权限。”

### 10.1 所有者的规则：无法撤销的删除要求主密码

由所有者决定（2026-10-19）：凡是尚未置于主密码之后的不可逆操作，只要存在主密码，就必须再次输入主密码，这样在 5 次尝试内猜中的 PIN 绝对碰不到这些操作。按已构建的实现：

- `VaultService.requireMasterPassword(password)`：沿用 `verifyPassword` 的答复与记录（错误的是 `wrong_secret`，并记录为 `unlock_failed`；空串是输入失误）；第 0 阶段的设备密钥保险库没有密码，直接放行（任何人在那台设备上本来就能打开它）。
- **永久删除**（`purgeForever`，回收站的行按钮和“彻底清除 …”）：密码是一个参数，在服务中最先检查；回收站显示一个主密码输入框并附原因（`eraseNeedsPassword`）。
- **同步部分的删除：** 加入之前保留的保险库和暂存的保存（`gateway.ts discardKept`、`discardParked`，经 `panel.ts`）：同样先做该检查；它们的确认对话框新增该输入框。
- **已核查，已经在它之后或并非不可逆：** 导出、新恢复密钥、密码变更、轮换、重置（恢复密钥）、清除安全记录、移除 PIN、每一个同步 `pw_auth` 操作（关闭同步、撤销、删除账户、清除服务器历史）。移入回收站、恢复、导入（只是合并）以及结束快速解锁，都是可逆的，或只是取消一条入口。“重新开始”仅在数据不可读时才存在，那时无从检查主密码；它本来就要求设置一个新的。
- 测试：`quick-pin-races.test.ts`（PIN 解锁之后，永久删除在以下情形被拒绝：不输入、输错、或把 PIN 当作密码；什么也没被清除，记录了两次 `unlock_failed`；输入正确的则可清除；设备密钥保险库无需密码）、同步面板的测试（输错密码什么也不删）、一项 e2e（回收站的输入框）。变异体 R2-12 至 R2-15。
