# AUTOFILL1 notes: TOTP autofill, Stage 1 (the Fill button and the Fill shortcut)

> **Round 2** (after the independent review, `AUTOFILL1-REVIEW.md`, verdict "merge after fixes") and **round 3** (after its
> re-verification, `AUTOFILL1-R2-VERIFY.md`): §14 lists each finding, its fix, its test and its mutant (the r3 rows are round 3's);
> §15 is the Stage 2 compatibility section; §16 is the follow-up after round 3 (AUTOFILL1-FU); §17 is STORAGEGATE (no
> injection unless Sixkey's storage is closed to the page). The rest of this file describes the code as it is now.

`docs/design/proposals/TOTP-AUTOFILL.md` §12.2 splits the autofill train into stages. This package is **Stage 1**, "the
minimal-risk subset" of §0.6: the user, on a page registered for one of their accounts, sees a Fill button on the account's
card and Sixkey puts the current code into the page's code box when they click it, or when they press a shortcut. It is
store-safe in the sense the design means: **one new permission without an install warning (`scripting`), no host
permission, no `content_scripts`, no registered or persistent script, no network, no clipboard, no auto-submit.** The
prerequisites (§4.2) were merged earlier: [AUTOFILL-PRE-NOTES.md](AUTOFILL-PRE-NOTES.md).

It answers the owner's report (a real login page, "Task Admin", with a box "TOTP code (required after binding)", the popup
open with the matching account "ws Cloud" on top: "autofill and automatic recommendation are not done"). The page in the
screenshot is fixture 1 of the tests (§8), and its box scores exactly as the design intends only because the scoring was
tuned for it (§4, D1).

**Not in Stage 1** (§10): automatic suggestions on sites the user turns on (Stage 2), the rule corpus, signed updates and
alias domains (Stage 3), the `declarativeContent` toolbar hint, closed shadow roots, contenteditable cells, the in-page
button and every host permission it needs.

## 1. What the user sees

- **On a page registered for an account** (the account's Sites contain the page's host or a parent of it: the existing
  "This site" section): under the account's card, a button **Fill code into this page** when the page has a code box
  (**Fill code** when it has none yet), and above the list a strip that says so: _Code box found on this page_ / _No code box
  found on this page. Open the step that asks for the code, then try again._ (with _Look again_) / _No code box found. It may be in a
  frame from another site, which Sixkey cannot look into._ / _Sixkey cannot look at this kind of page (a browser page, the Web Store or a PDF)._ The top match's button is the filled, dark one (the recommended
  one); the others are outlined. In the popup and in the side panel alike.
- **Click Fill**: the code goes in, and the card says _Code filled. Continue on the page._ Nothing is pressed or submitted:
  the user clicks the page's own button.
- **With less than 5 s left in the code's period**, the card says _New code in 3 s…_ (with Cancel), waits for the next
  period and fills that code (§8.2). A period under 10 s uses half of it as the limit. If the user goes to another tab, or the
  page changes, during that wait, nothing is filled and the card says so: _Not filled: you switched tabs while Sixkey waited for
  the new code._ / _Not filled: the page changed while Sixkey waited for the new code. Try again._ (§16).
- **The page asks something first** when it must: _This page is not secure (http). Fill anyway?_ (an `http:` page that is
  not an IP address, M5); _Which box?_ when two boxes look equally likely (listed by number and the page's own short label);
  _Fill the box that has focus_ when only the focused box qualifies weakly (an explicit choice).
- **Several accounts registered for the site**: each card has its own button; the first is the recommended one.
- **"Possibly related"** accounts never get a Fill button: they keep the existing _Remember: … belongs to this account_
  line (M2). HOTP accounts get none (they make no codes yet).
- **The shortcut Alt+Shift+F** ("Fill the verification code on this page", changeable at `chrome://extensions/shortcuts`)
  fills without opening anything when the vault is open to the worker, exactly one account is registered for the page and
  exactly one code box leads. The toolbar icon shows **OK** for four seconds (tooltip: _Sixkey: code filled_). Otherwise it
  shows **!** with the reason as the tooltip, and opens the popup, or the side panel in that mode (§5, D12).

## 3. How it works, step by step

1. **The popup (or panel) opens on a tab.** `Main.tsx` already reads the tab's address (`activeTab`, granted by the click
   or shortcut that opened it). If the list has a TOTP account in "This site" (registered tier), it imports the Fill chunk
   and its text. Otherwise nothing of the Fill code is loaded and no script is run in the page.
2. **Look.** `FillBar` calls `scan(tabId)`: `executeScript({target: {tabId, allFrames: true}, files: ["inject/otp.js"]})`,
   then `executeScript({…allFrames…, func: () => __skOtp.inspect()})`. The finder runs in the extension's _isolated world_
   of each frame the browser lets the call reach, reads the shape of the page's inputs (type, autocomplete, inputmode,
   pattern, maxlength, name/id/class/`data-*` words, label and ARIA text, placeholder, the words next to the box), scores
   them (§3.1 of the proposal), and returns up to four boxes: an opaque one-use token, single or group, size, score, "sent"
   flag, a 32-character label. It writes nothing and reads no box value; it reads at most 600 inputs in 60 ms (more: `z`, "too complex"; the clock counts only after some work, D22), looks closely at no more than 16 boxes (D20), looks at no document that is not an http(s) page, and a call that does not answer in 8 s is given up. Each frame's answer comes with the
   browser's `frameId` and `documentId`.
3. **Decide.** `candidatesFor(entry, tabUrl, frames)` keeps a box only if the account's registered domain covers the page's
   host (`matchTier === "registered"`, M1/M2), the frame and every page above it are covered by the same domain and the page
   at the top is the tab's (M4). `choose` takes the leader if it leads by 20 (§3.7) and fits (a group of exactly the code's
   length; a single box that takes at least as many characters).
4. **Click.** `fillCand` waits if under 5 s remain, then computes the code (`codeAt`, in the extension's own context) and
   makes the one call that carries a secret: `executeScript({target: {tabId, documentIds: [documentId]}, func: fill, args:
[code, origin, domain, topOrigin, token]})`. No `allFrames`, no `frameIds`.
5. **The page's second look** (`fill()` in the finder), before any write: the arguments have the right shape (6 to 8 digits;
   an http(s) origin; a host name); `location.origin` is the origin the extension matched and `location.hostname` is
   covered by the domain; in a frame, `location.ancestorOrigins` ends with the top page the extension looked at and every
   ancestor is covered by the same domain; the token is still in the table (one use), the box is still connected, visible (the deep test, D20),
   enabled, writable and still not a vetoed field; the code fits. Then it writes with the native `value` setter and
   dispatches `input` and `change` (React, Vue, Angular and Svelte see a user edit), reads the value back, and answers
   with an enum. For separate boxes it sets each (no focus call), then reads them back; if the page rewrote them, it focuses
   the first box and tries one synthetic `paste` event on it carrying its own `DataTransfer` (the clipboard is never touched).
6. **Report.** The panel shows _Code filled_ or the reason (_The page changed_, _The page did not keep the code. Type it
   yourself._, _The code was entered, then the page changed_ (D25), _The page did not answer in time_ (D22), _too short for this account's 8-digit code_). Nothing is stored, logged or copied. One automatic second try
   happens only when the document changed under a click (a rescan, not a second fill into the same box).

The shortcut does steps 2 to 5 in the service worker (`fillOnTab`) after reading the vault with `openView()`: the vault key
must be in the session (standard mode; "lock every time" never is, and a locked vault is the popup's), the vault is read
and not kept, no activity is counted (it does not move the idle deadline).

**What the always-loaded popup code grew by**: the glue (an `import()` of the Fill chunk with its preload list, one state, one
effect, one slot in `List`) and the modules the Fill chunk shares with the list (`core/match.ts` is now its own shared

appearing after one extra local chunk (a few milliseconds; the frame is drawn first). No limit was raised, and no text
moved: none of the Fill words is in the popup catalog (it keeps its 189 keys).

### 6a. One lookup for lazy text (round 2)

QUICKVIEW's View menu and the Fill button each keep their text in a lookup of their own, never in the page's catalog
(`src/ui/i18n.ts`), so a chunk that cannot be read costs that part its words and nothing else. The two copies are now one helper,
`src/ui/lazy-text.ts` (`lazyText(load, report)`): this language's catalog, else English's, else `words()` is null and the part
draws nothing of its own (the Fill UI draws nothing at all; the View menu says so in the page's words, as QUICKVIEW decided).
It is imported by the two lazy chunks only, so it is in no counted bundle (the popup did not grow). **Still two build
mechanisms**, on purpose and cheap to merge later: the View menu's keys are keys of the full catalog placed in a "view" part
(`stop: VIEW_ENTRIES`, `viewKeys`, `catalogs/view-<lang>.json`), the Fill button's are a disjoint catalog (`AUTOFILL_EN/ZH`,
`pageCatalogs`, `catalogs/autofill-<lang>.json`) with its own budget and check-dist rules. One rule for "popup sub-catalogs" would
replace both; it is a build change of its own and was not made in this patch.

## 15. Stage 2 compatibility (not built; the owner wants: an in-page suggestion, then PIN or fingerprint, then the fill)

What Stage 1 already fits, and what has to be settled first:

1. **Stable per-box tokens** are in (D23): a registered content script's observer can look as often as it likes while a person
   authorises, and the pending token still means that box. The table keeps a token until a fill spends it; the next look hands it
   out again.
2. **Fix the finder's cost first** (m-5): done here. An observer must additionally keep to the per-batch budget of §3.6 (the same
   `deadline` machinery), and report `z` instead of looking at a page that is too big.
3. **Where the authorisation happens.** The PIN or fingerprint prompt must be a surface the page cannot reach: the popup, the side
   panel, or an extension window, never the page. Opening any of them from a click on an in-page suggestion goes through a message
   to the worker, and **a user gesture does not survive the awaits of an MV3 worker** (m-7): `sidePanel.open` and, probably,
   `action.openPopup` need it. Choose the surface early and probe it on real Chrome (P4): the likely shape is a message sent from the
   content script _in the click handler_, answered by the worker _without awaiting before_ `sidePanel.open`/`openPopup`, or an
   extension window (`windows.create`, no gesture needed). The shortcut has the same rule today (D21).
4. **After the unlock.** The worker fills only with a key in the session. A PIN unlock leaves one (QUICK-UNLOCK), the PIN session
   parks it under the PIN otherwise; so the authorising surface should compute the code itself and call `fillCand` (the popup path),
   or leave the key long enough for the worker, re-checking the lock after the wait as the shortcut now does (M-1). A biometric
   unlock (QUICK-UNLOCK stage 2) is the same shape.
5. **The fill path stays**: the code is computed in an extension context after the user's trusted action and travels only as
   `args` of a call pinned to one `documentId` (check-dist now pins that shape in the build); `candidatesFor` and the finder's second
   look carry over unchanged. The content script channel (§4.3) adds message rows to `sender-policy.ts`; the exhaustiveness tests
   will fail until they exist.
6. **Clickjacking (K3)** and the in-page UI itself are new and not started: nothing in Stage 1 draws in a page.

## 17. STORAGEGATE: no injection unless Sixkey's storage is closed to the page (after `AUTOFILL2-PLAN-REVIEW.md` M5)

**The gap.** `storage.local.setAccessLevel` exists only from Chrome 140 (Chromium commit a8f1f337, M140). On Chrome 120 to 139
the worker's call at start fails (one diagnostics line), `storage.local` stays open to content scripts, and Stage 1 still
injected its look and its fill: a renderer that hosted one of them could read the encrypted vault (an offline guess at the
master password; the whole vault for a Phase-0 device-key vault) and write it (deletion, weakened settings). `storage.session`
is closed by default on every version.

**The gate.** `storageClosed()` (`src/platform/storage-access.ts`) asks the browser for TRUSTED_CONTEXTS on both areas, now, and
answers `true` only if both were accepted within 5 s (`GATE_MS`): a missing method, a throw, a rejection or no answer is `false`.
It remembers nothing, so no answer outlives a worker restart or a browser update. `src/platform/autofill.ts`, still the only
caller of `chrome.scripting`, awaits it at the top of `scan()` (before the install and the look) and in `fillCand()` before the
fill (after the wait for the next code; the code is then not even worked out). Every path goes through these two: the look when
the popup or panel opens, the press (its own looks and its fill), and the shortcut (its look and its fill). A refusal is `gated`.

**Where the truth lives: the context that injects asks the browser itself.** The popup, the side panel and the worker are all
trusted contexts, which may call `setAccessLevel`; the call is idempotent and cheap, and its answer is the browser's state at
that moment. Asking the worker instead would need a new message type in the sender policy, would fail when the worker is asleep
or restarting, and would hand back an answer from the worker's start (older than the injection). The e2e build's Chromium 156
accepts the call from the pages (every autofill test would be `gated` otherwise).

**What the user sees.** Gated: the look does not run, no Fill button is drawn (and no _Look again_), and the strip says
_Autofill needs Chrome 140 or later._ (zh_CN: _自动填写需要 Chrome 140 或更高版本。_). A press whose fill is gated, or whose own look is (the verify's NIT-4,
AUTOFILL2-NOTES §6), says the same under the card. The shortcut shows **!** with _Sixkey: autofill needs Chrome 140 or later_. The same line shows if the call fails on
Chrome 140 or later (not expected; the diagnostics line names the area). `minimum_chrome_version` is unchanged (owner question
OQ1, `OWNER-DECISIONS/14`): raising it to 140 is a one-line change for later, and this gate stays as defence in depth.

**Residual [inferred, from the review].** A renderer that hosted an injection on Chrome 120 to 139 before this patch may keep its
access to `storage.local` for the life of that process: the update stops new injections, it does not revoke an old grant.
Closing those tabs, or restarting the browser, ends it.
