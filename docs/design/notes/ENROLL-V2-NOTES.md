# ENROLL-V2 notes: the approval join with a 128-bit pairing code

`docs/SYNC-DESIGN.md` revision 27 (§0.0aa; §2.2, §2.6, §3.2 with MUST 5 and MUST 10, §6 O5, O6, O9, §7, §8.1, §10 rows
1, 28, 109, 110) replaces the approval join's key agreement: the key that protects the device name the new device
reveals and the payload that carries the vault key is now

    K = HKDF-SHA256(IKM = Z ‖ S, salt = h, info = "sixkey/v2/enroll-key")

where Z is the ECDH P-256 secret and S a 128-bit pairing secret that the approving device draws when it answers the
request, shows once (28 characters, the recovery key's layout), and that the user types on the new device before it
reveals anything. Sixkey never sends S. A recording of the whole join is therefore useless to anyone who later solves
ECDH (a quantum computer): the "harvest now, decrypt later" exposure `docs/design/proposals/PQ-READINESS.md` found is
closed. The 6-digit SAS stays (the new device shows it, the approver types it, three tries) as the approver's second,
independent check. The confirmation code (CC) is gone. Nothing had shipped, so there is no migration: v1 is replaced.

This package implements that revision in the contract, the engine, the Sync section and the tests. `SYNC-DESIGN.md`
itself was already at revision 27 and is not part of it. This is the package's second revision: §9 lists what the
maintainers' independent review of the first (`ENROLLV2-REVIEW.md`, not part of this patch; verdict "merge after
fixes") found and what was done about each finding, including the contract text (`api/openapi.yaml`), which now
describes enrolment v2 too (§4).

---

## 1. What changed

### 1.1 The contract (`contract/`)

- **Vectors** (`contract/vectors/sync-v1.json`, regenerated by `contract/tools/gen-vectors.mjs`):
  - `labels`: the seven version-1 enrolment entries are gone (the HKDF label `sixkey/v1/enroll-key`; the tags
    `sixkey-enroll-commit|1|`, `sixkey-enroll|1|`, `sixkey-enroll-name|1|`, `sixkey-enroll-payload|1|`,
    `sixkey/v1/enroll-sas|` and the CC's `sixkey/v1/enroll-confirm|`); in their place the HKDF label
    `sixkey/v2/enroll-key` and the tags `sixkey-enroll-commit|2|`, `sixkey-enroll|2|`, `sixkey/v2/enroll-sas|`,
    `sixkey-pairing-code|1|`, `sixkey-enroll-payload|2|`, `sixkey-enroll-name|2|`. Still 12 labels (one Phase 0-only)
    and 16 tags; the distinctness and prefix-freedom assertions cover the new ones.
  - `enrollment`: `inputs` gains `pairing_secret_hex` (S = 38 39 … 47), `pairing_code` (its text) and `ikm_hex`
    (Z ‖ S). Every derived value is recomputed: commitment, transcript, h, K, SAS, the reveal name and the payload
    (`v: 2`), the substitutions (SAS only), the MITM (its note rewritten for the two cases, S known or not), the commit
    checks. `cc` and `cc_u32` are gone, and `mitm` lost `cc_expected_by_N` and `cc_shown_by_A`. `must_not_open` has 16
    cases now, among them: K from Z only (the literal v1 derivation, for the payload and for the name), K from Z only
    under the v2 label, S with its last bit flipped (name and payload), the IKM in the wrong order (S ‖ Z), and the right K
    with the v1 AADs. `label_swap` is now the check-bit domain test: the same 16 bytes as a recovery key and as a
    pairing code, with both 12-bit check values, and each rejected where the other belongs.
  - `sas_cc` is renamed `sas` (SAS cases only, under the v2 tag); a new group `pairing_code` holds four formatting
    cases, seven equivalent inputs (case, spaces, `-`, `_`, O/I/L, surrounding whitespace) and eight rejected inputs
    (a typo the check bits catch, 27 and 29 symbols, empty, `U`, `*`, the recovery key of the same secret, and the
    `recovery_auth` group's recovery key).
  - `wire_examples`: recomputed through the generator (the create body's `commit`, the reveal's `name_ct`, the approve
    body's `transcript_hash` and `payload`, N's `approved` view, A's `revealed` view). The respond example and the
    approve body's `name_ct` (under K_name of the VK) are unchanged, as the design says. A field-by-field diff of the old
    and new file shows exactly these five examples and the groups `labels`, `enrollment`, `sas`/`sas_cc`,
    `pairing_code` changed, plus the file's `source` line; `recovery_auth` and every other group are byte-identical, so
    the recovery key's untagged check bits are unchanged.
- **Schema** (`sync-v1.schema.json`): the groups list, the label pattern (`^sixkey/v[0-9]+/…`), the enrolment shape
  (`inputs`, `mitm` and `label_swap` closed; no `cc`), `sas`, `pairing_code`, and a `code28` definition.
- **Generator**: one tagged codec for both codes (`codeText`, `codeParse`), the v2 enrolment, `genSas`,
  `genPairingCode`; its self-checks assert among others that K is the HKDF over the 48-byte IKM, that the two check-bit
  domains differ for the fixed S, and that every rejected input fails with its stated error.
- **Python reference** (`contract/py/sixkey_contract.py`): the codec with a tag (`code_format`, `code_parse`; the
  recovery functions keep their names), `enroll_key(z, s, h)`, `v_enrollment` rewritten (it recomputes the key of every
  named `must_not_open` case instead of trusting it), `v_sas`, `v_pairing_code`; `v_labels` also asserts that no
  version-1 enrolment tag is listed. `contract/py/test_contract.py` adds four tests: the verifiers refuse
  fourteen regressions (K from Z only, the v1 key, payload `v: 1`, the v1 name AAD, the v1 commitment tag, a `cc`
  member, an IKM without S, untagged check bits in `label_swap` and in the `pairing_code` cases, a missing Z-only case,
  a `pairing_code` group without the recovery-code case, the v1 SAS tag, a listed confirm tag, a label list without
  `sixkey/v2/enroll-key`), the Python codec's own reading, the schema refusing a `cc` (or any unnamed) member at the
  enrolment group's level, and H8 refusing a v1 tag, an unknown label or the CC in the contract's text.
- **`check_consistency.py`** H8 now reads labels and tags of any version (`sixkey/v\d+/…`, `sixkey-…|\d+|`), in the doc
  and, since revision 2, in `api/openapi.yaml` too (every label or tag it names must be one the vector file lists, and
  it must not name the CC). Before this package it reported the 8 enrolment mismatches the design predicted; now 0.

### 1.2 The engine (`extension/src/core`)

- `core/crypto/recovery-code.ts`: the codec takes the check-bit tag as a parameter (`formatCode`, `parseCode`; the
  recovery key keeps the empty tag, so its bytes are unchanged); a failed checksum also wipes the candidate secret
  (a typo of S is a few bits from S; revision 2, R-7).
  `core/crypto/pairing-code.ts` names the pairing kind: `PAIRING_CODE_TAG`, `generatePairingCode`, `formatPairingCode`,
  `parsePairingCode` (errors `pairing_length`, `pairing_char`, `pairing_checksum`, added to `CryptoErrorCode`).
- `core/sync/crypto/enroll-labels.ts` (new) holds the enrolment's label and six tags; `labels.ts` keeps the rest.
- `core/sync/crypto/enroll-crypto.ts`: `enrollKey(z, s, h)` over Z ‖ S, wiping Z, S and the IKM whatever happens and
  refusing wrong lengths; P is `v: 2` and only `v: 2` is read; `ccOf` is gone.
- `enroll-approver.ts`: a new first phase `responding`. `start()` draws S (from `crypto.getRandomValues`; the
  `pairingSecret` test seam is not reachable through the public index), and the respond body is `{epk}` only.
  `respondAccepted()` (after the server's 200) moves to `awaiting_reveal`, the only phase in which `pairingCode` is
  readable. At the reveal S goes into K and is wiped; a name that does not decrypt under K ends the request as
  `pairing_mismatch` (a name that decrypts but breaks §2.4 stays `bad_name`). `Approved` has no code; `#cc` is gone.
  Every failure wipes S.
- `enroll-new-device.ts`: the phases are `requesting → waiting → entering_code → showing_sas → accepted`.
  The first `responded` pins (devA, epk_A) and asks for the code; nothing is revealed and no SAS exists before it.
  `submitPairingCode()` answers `malformed` (length, symbols) or `wrong_code` (check bits) locally, with no state change
  and no attempt counted, any number of times; a good code gives T, h, Z, K, the SAS (once) and the reveal body, and
  S is wiped. The `approved` poll opens the payload at once: anything that does not open under K, or does not hold
  together (approver, vaultId, MAC, version), is the terminal `bad_payload`. `submitConfirmationCode` and
  `cc_mismatch` are gone.
- `core/sync/engine/enroll.ts`: `ApprovalJoin.poll()` reports `enter_code`, `show_sas`, `approved`; `submitPairingCode()`
  sends the reveal; `prepare()` makes the join from the opened payload (the fold that used to run after the CC). Polls
  and the code step run one after the other, so a poll that lands while the code is checked waits instead of tripping
  the machine's one-transition guard. `bad_payload` rejects the request and removes the pending identity (as `cc_mismatch`
  did). `Approver.start()` calls `respondAccepted()` after respond's 200 and exposes `pairingCode`;
  `Approver.poll(password)` rejects the request (pw_auth) at every failure the poll finds (`pairing_mismatch`, a
  commitment that does not open, a changed pinned value, a reflected key, a state ahead of this side), as three wrong
  SAS do; `Approver.reject` ends the machine before its own check, so a reject refused by a lock still wipes S;
  `Approver.start` asks respond again (twice at most, the same body) when its answer is lost; `Approver.discard()` ends
  the machine (and S) without a request; `submitSas` returns `{kind: "approved"}`.
- `devsync/main.ts` (dev and e2e builds only): `approverPairingCode()`, `approverPoll(password)`; the page's one
  approval is discarded at a new pick and at `pagehide`.

### 1.3 The Sync section (`extension/src/options`)

- **Approving device** (`approve.ts`, `ManageViews.tsx`): after respond, the step `code` shows the pairing code in seven
  groups (focus moves to it; screen readers get it symbol by symbol), Copy, the note on what copying means (§7: the
  system clipboard, a clipboard shared across devices, the 30-second clean-up when the user turned it on), the scam
  warning and a waiting line; the page polls until the new device reveals, which takes the code off the screen and out
  of the flow's state. Then the SAS step as before; a name that does not open is the step `mismatch` ("the pairing code
  did not match … start again on the new device"); a match is `done` ("Approved. The new device is finishing joining.").
  The CC screen and "I typed it there" are gone. Every end of the flow ends the machine (`discard`), so S is wiped at a
  lock too. The code is on screen at most `CODE_LIFETIME_MS` (the request's 600 s and a minute) from respond's
  acceptance, by this device's clock, whatever the polls say; then the flow ends as expired. If the user copied it, the
  clipboard is cleared of it as soon as its step ends (the reveal or any end), when clearing is allowed.
- **New device** (`join.ts`, `JoinView.tsx`): after the request, the step `code` asks for the pairing code (the shared
  28-character input, paste allowed), says "That is not a pairing code" or "This code has an error" without counting
  anything, then shows the SAS dial. A request that ends after the reveal is said as "The request has ended. If the
  pairing code was mistyped, start again." (`join_ended`; this side cannot know why it ended). The CC step is gone.
  The code typed is held by the view only while its step is on screen.
- **One 28-character input** (`shared.tsx CodeField`, with `code-text.ts`): used by the recovery-code join, the turn-on
  step 4, the key operations and the repair (`RecoveryField`), the new device's pairing code (`PairingField`) and the
  forgotten-password reset (`Reset.tsx`). See §1.4 for how it is masked. It keeps every symbol typed: a 29th is not cut
  off, the field says "Too long: the code has 28 letters and digits" (the Sync fields) and marks itself invalid, and
  the code's own reading refuses it (`pairing_length`, as the vectors say).
- Comments that named the CC are rewritten (`account.ts`, `approve.ts`, `join.ts`, `JoinView.tsx`, `widgets.tsx`,
  `sync-flows.ts`). The other files the grep found (`Reset.tsx`, `enable.ts`, `fork.ts`, `keyops.ts`, `revoke.ts`,
  `codesteps.tsx`, `ManageViews.tsx` outside the approval, `SyncSection.tsx`) only use "confirmation" in another sense
  (a typed confirmation, a review): false positives, left as they were. `docs/ARCHITECTURE.md`'s three lines about the
  enrolment are updated.
- **Text** (`extension/scripts/i18n`): a new fragment `enroll2.py` with eleven Sync-catalog keys (en and zh_CN). The
  Sync catalog has no OVERRIDE or REMOVE, so the CC's keys (`syncCcTitle`, `syncCcBody`, `syncCcLabel`, `syncCcMalformed`,
  `syncCcWrong`, `syncFailCcMismatch`, `syncApproveCcBody`, `syncApproveFinished`) are deleted from `m6.py` and `m6b.py`
  and five texts rewritten there in place (`syncWaitingStep3`, `syncSasBody`, `syncScamWarning` now "these two codes",
  `syncApproveWaiting`, `syncApproveDone`); nothing had shipped. The generated catalogs are not in the patch
  (`scripts/messages.py`'s rule; §8); the full catalogs (`_locales`) do not change.

### 1.4 The maintainers' later requirement: no code in a text field

Chrome may keep a text field's value for session restore (verified for web pages, not for extension pages); it does not
keep a password field's. So every input that takes a recovery key or a pairing code is a password field:

- `CodeField`: `type="password"` until the user ticks Show (a labelled checkbox that controls the field; the page's
  existing word "Show"), `autoComplete`, `autoCapitalize` and spell checking off, no `name`; paste allowed. Shown, the
  value is grouped as typed; hidden, it holds the symbols only and seven bars under it count the full groups, and the
  count "n/28" is in the field's description for screen readers. It empties itself at `pagehide`, at a lock from any
  page (the password-setup change's pattern, `LOCK_EPOCH_KEY`) and when it unmounts (its step ended), and each time
  tells its owner (`onValue("")`), whose state drops the value too.
- The two groups of a new recovery key typed back (`codesteps.tsx`, `EnableView.tsx`; `GroupFields`): the same, one Show
  for both, emptied at `pagehide` and at a lock.
- The popup's "use recovery code" (earlier name) field (`Locked.tsx`): a password field with its own Show (a labelled checkbox under
  it, `#secret-show`, hidden again at every change of mode); the master password and the PIN in the same field can
  never be shown. Nor can the master password in the grouped boxes the input hint may bring there
  (PASSWORD-SETUP-NOTES.md §8.3): the popup draws `PasswordGroups` with `showable={false}`, so it has no Show at all
  (owner decision on the POPSEG review, MINOR-1). The same source-rule test checks both.
- A source-rule test fails on any `type="text"` input outside a named list (issuer, label, the TOTP secret of the manual
  add form, the DELETE confirmation, the device name, the six-digit fields, the popup's search) and on any computed type
  other than `shown ? "text" : "password"`.

`sync-crypto-adversary.test.ts` drives both production machines with a hostile server (two-session MITM), in the two
cases of §8.1: without S, zero wins at the 4-bit and the full SAS (800 + 800 sessions, plus the grinding and re-reveal
variants), A always ends with `pairing_mismatch` before the SAS step and N with `bad_payload`; with S leaked, against A
about 1/16 at 4 bits (101 of 1600, inside ±4σ, and 103 of 1600 with the re-reveal variant: one guess, not three), zero
of 2000 at full length, grinding after N's SAS breaks the commitment (all `commit_mismatch`), and the ablation (an
approver that would not pin C) loses 200 of 200; and N accepts the impersonating server's vault in every session (400 of
400, and 2000 of 2000 at full length), asserted under the name of §10 row 110 as the accepted residual. The "quantum"
adversary handed Z opens neither ciphertext with HKDF(Z, h) under the v1 or v2 label or with a guessed S, and none of
the payloads it forges with those keys is accepted. Replay of an old payload, an old request's code, reflection and an
unknown key share are refused.

## 3. Deviations from the request or the design

1. **The pairing functions are exported by `core/crypto/pairing-code.ts`**, not by `recovery-code.ts`. The codec is
   the recovery key's (one implementation, a tag parameter); only the naming of the pairing kind lives apart.
   Reason: `recovery-code.ts` is in the chunk the popup loads, and the pairing functions would have been kept there in
   the gate-open build (the options page uses them), growing the popup.
2. **The enrolment labels live in `core/sync/crypto/enroll-labels.ts`**, not in `labels.ts`. Same reason: `labels.ts` is
   in the popup's shared chunk. As a side effect the store build with the gate closed no longer ships any enrolment tag.
   The label tests count the three sets together, as before.
3. (Revision 1 kept `CC_ATTEMPTS` for `api/openapi.yaml`'s sake; revision 2 removed it from both, §4.)
4. **`Approver.poll` takes the master password**, so that the engine itself rejects the request at `pairing_mismatch`
   (the reject needs pw_auth, S8), as `submitSas` already did for three wrong SAS.
5. (Revision 1 left the popup's recovery field masked without a Show toggle; revision 2 added one, §1.4, §9.)
6. **The text fragments `m6.py` and `m6b.py` are edited in place** (the Sync catalog supports new keys only).
7. **`docs/ARCHITECTURE.md`** is updated (three lines), although not listed.

## 4. The contract's text: `api/openapi.yaml`

No request or response shape changes, as the design says: the server needs no change (`name_ct` is still 188 bytes and
the payload as long; `api/server` names no CC field or constant). Revision 2 rewrote what the file still said about
enrolment v1, in one change with what depends on it:

- **Descriptions**: `GET /v1/account` ("the real protection is the pairing code", not the CC); `POST …/reveal` (the
  name's AAD `sixkey-enroll-name|2|`, and K_enroll over Z ‖ S with the v2 label, S never in a request); `POST …/approve`
  (nothing is shown after its 200: the code was shown after respond's, and the new device uses only a payload that opens
  under K_enroll); `POST …/reject` (the new device rejects its own request when its payload does not open,
  `bad_payload`); `EnrollPayloadCiphertext` (AAD `sixkey-enroll-payload|2|`); the create body's `commit`
  (`sixkey-enroll-commit|2|`).
- **`x-sixkey-constants.CC_ATTEMPTS`** is gone, with `SYNC_CONSTANTS.CC_ATTEMPTS` (`constants.ts`); the `enroll-v2`
  source rule now allows no `CC_ATTEMPTS` anywhere in `src/` and no `CC` in the contract. `sync-crypto-hygiene` (every
  client constant mirrored) stays green; neither `contract/py`'s required constants nor the server's tests named it.
- **H8 reads the contract too** (`check_consistency.py`): a label or tag in `api/openapi.yaml` that the vector file
  does not list, or the word CC, is a hard mismatch; `test_contract.py` checks that it catches a v1 tag, an unknown
  label and the CC in a copy of the file.

## 5. Where the design was ambiguous, and what was chosen

1. **"S discarded at every end"** on the approver: S is wiped at the reveal (K holds it from then on), not at approve.
   The code text is a JS string and cannot be wiped; its references are dropped at the same moments.
2. **The Copy exception and the clean-up message**: the clipboard clean-up sends `SHA-256(text)` to the service worker
   (the existing mechanism for every copied code). It is not S and not an online oracle (it never leaves the extension),
   but it is derived from S; it is read as part of the Copy exception and documented here. The hash lives only in
   memory: the worker passes it to the offscreen document, whose 30-second timer compares it with the clipboard and
   then closes the document; nothing stores it. `runtime.sendMessage` reaches every open extension context, not only
   the worker: the same trust domain, so harmless. The test asserts the message holds the hash, never the text.
   Clearing needs the user's clipboard permission (`clipRowTitle`); the note says "if clearing the clipboard is on", as
   §7's "在用户允许时" does. Since revision 2 the step's end also asks for a clean-up at once (the offscreen document
   waits at least a second), so the code does not stay on the clipboard for the whole 30 seconds after the reveal.
3. **`bad_payload` scope**: the design names the payload that does not decrypt. A payload that decrypts but does not hold
   together (another approver, vaultId, bad bundle MAC, another version) is the same terminal failure, with the same
   reject and identity removal.
4. **No attempt count for the code**: format and check-bit errors are free and unlimited (they are local and reveal
   nothing); a typo past the check bits costs the request, as the design says.
5. **"Format wrong" vs "code wrong"**: not 28 symbols of the alphabet → "format"; check bits → "code". Continue is enabled
   once 28 symbols are there (as for the recovery key), so the format message is what a symbol outside the alphabet
   gets.
6. **What N says after a mismatch**: only an end that comes after N revealed is said as "perhaps mistyped"
   (`join_ended`); an end before it keeps the old wording.
7. **The reading** inherits the recovery key's: `_` is ignored too, not only spaces and `-`.
8. **A lock on the approver** ends the machine without a reject (the request expires on the server), as M6's lock did
   for the approval; Cancel and the page closing still reject with the password. A lock while respond is on the wire
   ends the machine as well: the late reject that follows ends it first, whatever its own check says (R-1).
9. **Paste** is the field's native paste (no `onPaste` handler); its `maxLength` of 64 lets the 34-character grouped form
   and surrounding whitespace in.
10. **The code's lifetime on the approver** (MUST 10, "至多到请求过期"): counted from respond's acceptance on this
    device's clock, the request's 600 s and a minute of rounding (the bound the new device already uses), applied while
    the code is on screen; after the reveal S is gone and the request's own end is the server's word.
11. **"The request was rejected"**: the mismatch screen now says "This request is over", since the reject the engine
    sends may itself fail on the network; the flow is over either way, and the request expires on the server.

## 6. Residuals

- **§10 row 110** (accepted by the design): S leaked to the server side → the server can pose as the approver to N. The
  adversary test asserts it as such.
- **The clipboard**: Copy goes through the system clipboard; a clipboard shared across devices may carry it away
  (said beside the button); the clean-ups (30 seconds, and at the step's end) run only when the user allowed clipboard
  access.
- **A pairing code typed into the recovery join** passes the recovery key's check bits about 1 in 4096 times; then
  `recAuth = HKDF(S, "sixkey/v1/recovery-auth")` reaches the server, a one-way value of S that does not help compute
  K = HKDF(Z ‖ S, h). Named here for completeness (the review's §2); no design change.
- **Unverified**: whether Chrome's password manager offers to save a password field on a `chrome-extension://` page
  when its form is submitted. If it does, that is a worse prompt than the session-restore risk it replaces; the fields
  have no `name` and `autoComplete="off"`.
- **Not in scope, same class**: the manual add form's TOTP secret (`AddAccounts.tsx` `#m-secret`) is a text field.
