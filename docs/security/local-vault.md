# Sixkey security notes (Phase 0.x, local only)

> This file was `docs/SECURITY.md` until 2026-10. How to report a vulnerability is in the repository's root
> [`SECURITY.md`](../../SECURITY.md).

This describes what the code in `extension/` does today, what it protects against, and what it does not.
It is a description of the implementation, not a promise about anything not yet built. "Phase 0.x" is Phase 0 plus the
hardening items H1–H8 and the usability work U1 and U1b (`docs/history/PHASE0X-PLAN.md`).

This version **sends nothing over the network**. The server sync of Phase 1 (`docs/SYNC-DESIGN.md`) is removed from
the extension (OWNER-DECISIONS/25): no build has its client, neither the settings page's Sync section and the developer
sync page that turned it on (DV-0a) nor its engine, worker, bridge, transport, API origin and host permission (DV-0b);
`scripts/build.mjs` and `scripts/check-dist.mjs` fail a build of any flavour that contains them, and check-dist fails
one that names its API's address anywhere. Nothing in the extension sends a request, but, in a build whose release
gate lets it in (the development and e2e builds, not the store or test builds), the site rules' updater's one read once
it is switched on.

What the browser enforces:

- **No host permission at install.** The store, test and dev builds' manifests declare one _optional_ host permission
  and nothing required: `https://*/*`, from which TOTP autofill asks for one site at a time (exactly `https://<host>/*`,
  in the click that turns code suggestions on for it). The e2e build has no optional host permission: only two test
  hosts, required, granted up front (its tests cannot answer Chrome's prompt). A site's grant is
  access to that site's pages, not to the network: the content-security-policy below names no other origin. A host
  permission only grants: it lets requests to that origin past the browser's cross-origin rules. (The dev and e2e builds
  also declared the server sync's API origin, with its own checks before every request, until that sync's client went:
  DV-0b.)
- **What restricts is the content-security-policy.** It covers the extension's pages and its service worker alike:
  `connect-src` is `'none'` in the store build (with the site rules' updater's release gate open, as in the development
  and e2e builds, it names that updater's one path alone) and `img-src` is `'self' data:`. Every extension page also
  carries its own policy, `connect-src 'none'`, which the browser enforces on top of the manifest's, so no page can
  reach any host. Only the service worker could reach that one path. Code in the worker that skipped the extension's own
  checks (compromised extension code, say) gets nothing onto the wire to any other address, not even a CORS-simple
  request or a preflight: the browser refuses it before it leaves (`test/regression/permission-wire.spec.ts`).
- No declared content scripts. Sixkey injects one small script of its own into the tab you are on, only on your action (open Sixkey on a page registered for an account; Fill; the Fill shortcut), with `activeTab` (see "Permissions"). On the sites the user turned code suggestions on for (TOTP autofill Stage 2, `docs/design/notes/AUTOFILL2-NOTES.md` §9), the same finder and a small content script are registered to run in that site's pages, only while `storage.local` and `storage.session` are closed to content scripts; they look only after the user's own click or key press in a box, write nothing to the page, and send the worker one message with no field, which sets the toolbar badge.

What the build enforces (`scripts/check-dist.mjs`, `npm run check`, part of `npm run verify`): the manifest is exactly the
expected one (permissions, the optional host permissions and no required one, the policy); every page carries its
own `connect-src 'none'` ahead of its first script; `fetch` appears in the store build's shipped code only for the
package's own site rules (`chrome.runtime.getURL`, no network), and with the site rules' updater's gate open once more,
in the service worker; no other network primitive appears at all; and no URL appears but, in that worker, the rules
origin's, apart from XML namespace names, the hostname parser's `http://${host}/` template and an autofill site's
permission pattern `https://${host}/*`, none of which is ever fetched; and the server sync's API origin appears in no
shipped file of any build.

A regression test (`test/regression/network.spec.ts`) tries fetch, XHR, image, WebSocket and beacon requests from the
popup and the settings page, and fetch from the service worker, against a local server and requires that nothing
arrives, and that neither a page nor the worker reaches the address the server sync's API origin had; with the extension
used meanwhile, that address gets nothing. Another (`test/regression/page-csp.spec.ts`) requires that no page reaches
the site rules' path, the manifest's one `connect-src` source in the e2e build, while the worker does.

## Reporting a vulnerability

Report it privately, through GitHub private vulnerability reporting or to [security@g.pro](mailto:security@g.pro);
the policy, its response times and its safe harbour are in the root [`SECURITY.md`](../../SECURITY.md). Please do not
file public issues for security problems.

## Cryptography

All primitives come from the browser's WebCrypto; there is no third-party crypto library.

- **Vault key (VK)**: 32 random bytes. The vault payload is encrypted with AES-256-GCM using a key derived from the VK by HKDF-SHA256 (`sixkey/v1/vault-enc`). A fresh random 96-bit IV is used for every encryption.
- **Envelope** (`core/crypto/envelope.ts`): header fields `vaultId`, `vkId`, `rev` are bound into the GCM additional data. The `checksum` is SHA-256 over header ‖ IV ‖ ciphertext. It never covers the plaintext, so it reveals nothing about the contents and can be checked while locked.
- **Wrapping the VK** (`core/crypto/keyring.ts`): AES-256-GCM, with additional data binding method, key id, vault id and the KDF parameters, so none of those can be swapped.
  - _password_: PBKDF2-HMAC-SHA256, 16-byte random salt, password normalised with NFKC. Every new master-password wrap (first run, restore, start over, turning the password on, a change, the reset, a key rotation) uses 2,000,000 iterations (`PBKDF2_PASSWORD_WRAP_ITERATIONS`, measured in Chrome: docs/design/notes/OWN-PASSWORD-NOTES.md §2). A wrap is read at the count it carries, between 600,000 and 20,000,000 (enforced when **reading** stored parameters too, so a tampered file cannot lower it): one made at 600,000 before 2026-10-22 still opens, and is re-wrapped at 2,000,000 at the next password change, never by an unlock. The sync engine's own wraps and its `pw_auth` keep 600,000 (docs/SYNC-DESIGN.md §3.14).
  - _recovery key_: 128 random bits + 12 check bits, shown as 28 Crockford base32 symbols. High entropy, so HKDF is used instead of a slow KDF.
- **Recovery key shares** were removed on 2026-11-25 (docs/design/notes/SHAMIR-NOTES.md): version 0.1.4 and earlier could split the recovery key into shares; this version neither makes nor takes them, so a recovery key kept only as shares can be rebuilt only with one of those versions. Entries of shares made, and a reminder to check them, that those versions wrote stay in the security record, unread and not listed, until it is cleared.
  - _device_: a random 256-bit key stored with the data. Not a secret against anyone who can read the profile. Only Phase 0 vaults that never got a master password still have one; nothing in this version writes a new one.
- **Changing the password**, **a new recovery key** and **the password reset** re-wrap the VK only. **Turning the password on** (for a Phase 0 vault) and the **replace key** action create a _new_ VK and re-encrypt everything. The old VK is kept only inside the new keyring, wrapped by the new VK, so older copies stay readable. This replaces the current copies on disk; it cannot erase bytes the database has already written and not yet compacted (see Limits).
- **Backup files** are independent: their own password, their own salt and iteration count, no device key and no keyring. Header fields are authenticated. A file of selected accounts uses the same format (see "Exports").

## Master password and first run (H1, H5)

- A new vault is made in a settings tab, in this order: master password, recovery key (shown, and confirmed saved), one question about the profile, then the first account. The keys are prepared in memory first (`prepareKeys`: a new VK wrapped by the password and by a new recovery key, no device key); nothing is written until the user finishes the question, and then the vault is written in one locked step. Closing the tab before that leaves nothing behind. The same steps are used for restoring a backup into an empty or unreadable profile and for starting over after typing DELETE.
- It runs in a tab, not in the popup, because the popup closes as soon as focus leaves it (for a password manager or the downloaded code file), and would close with an unsaved code.
- The question ("Is this browser profile used only by you?") picks one of the two security modes below and saves it in the same locked step, before the key: in "lock every time" mode the key then stays in that page's memory only.
- **The master password is the user's own** (OWNER-DECISIONS/15, 2026-10-22: a password one can remember, the PIN for every day, the recovery key for recovery only). The service enforces a floor wherever one is set: 12 characters, no obvious sequences or repeats, and not one of a short list of common passwords (`checkPasswordPolicy`, 10 entries); the settings page adds the real common-password floor below. The settings page also estimates its strength (`zxcvbn-ts`) at first run, turning on or changing the master password and the password reset. Below 10⁶ estimated guesses (about 20 bits, such as `Password1234`) the page refuses it outright, as too easy to guess. Between that and 50 estimated bits it is a warning, not a block: the page says that someone who copies the browser profile can guess offline, and how long one graphics card takes at that strength, and accepts the password only after "Use anyway" for that very value. Backup files' passwords (and the sync key operations, behind the release gate) keep 50 bits as their bar (docs/design/notes/OWN-PASSWORD-NOTES.md §1).
- For the master password, one's own comes first; "Generate for me" is the secondary choice after the fields. It stays the first choice for a backup file: 16 random characters from 31 (about 79 bits), or 5 random words from the EFF large wordlist (about 64 bits), drawn with `crypto.getRandomValues` by rejection sampling. For exactly the string a generator made, the page counts the generator's known entropy instead of the estimate; anything typed or edited is estimated as before (docs/design/notes/PASSWORD-SETUP-NOTES.md). A new password is never in a field the browser keeps for session restore: the fields stay `type="password"` (with `autocomplete="off"` while the user shows them), a generated password is shown as page text only, and the page forgets it on a lock, when the field is emptied and when the page goes away.
- **A generated password typed back loosely.** Every prompt that checks the master password (the lock screen, the settings unlock bar, the export, PIN, rotation, change, new-code, delete and clear-the-record prompts) and every backup file's password prompt also accepts a generated password without its hyphens, in lower case, or with spaces (words: with spaces, underscores or capitals). The string typed is tried first, exactly; only if it has a generated shape and fails is the generator's own spelling of it tried, once (`core/crypto/password-candidates.ts`, `openWithPassword`). So such an attempt costs one more key derivation, and one attempt can test two candidate secrets; it is still one entry and one count in the security record, so "N wrong attempts" means N attempts, each at most two secrets. There is no lockout, so the secrets tested per second of PBKDF2 do not change, and offline attacks are not affected at all. Nothing that sets a password uses this: the stored password is always exactly the one given, and a key rotation re-wraps the stored spelling, never a loose one. The sync engine's key operations still need the exact spelling (docs/design/notes/PASSWORD-SETUP-NOTES.md §7.5).
- **The input hint.** For a generated master password, `sk_pw_format` in `chrome.storage.session` (memory only, Sixkey's own pages) says which style it is and the salt of the wrap it belongs to, so the settings page and the popup's lock screen can show four groups of four (and the settings page the words' hint). It is never written to disk: on disk its presence or absence would tell a profile-copy attacker which passwords are the user's own. It survives a lock, goes when the browser closes, and the next password unlock notes it again; until then the prompts show the plain field. It is never used to decide anything.
- Phase 0 vaults without a master password keep working. The popup and the settings page warn, and Settings › Security › Turn on master password replaces the key as described above.

## Locking and the two security modes (H5, U1)

- Automatic lock (only with a master password): after N idle minutes (default 15), when the browser restarts, or every time the popup closes ("lock every time"). Separately, when the computer's screen locks (the `idle` permission). Updating or reloading the extension always locks.
- In the idle and browser-restart modes the unlocked key is held in `chrome.storage.session` (memory only, cleared when the browser restarts or the extension updates or reloads; on some systems closing the last window does not restart the browser), shared by Sixkey's pages. The service worker arms an alarm for the idle deadline and then removes the key from there; every use also compares timestamps, since a service worker can be stopped.
- In "lock every time" mode the key is never put in `chrome.storage.session`, and anything found there is swept out. It stays in the memory of the page that unlocked it, so closing the popup is the lock, and every popup opening asks for the password. A settings tab unlocked in this mode holds its own copy (see Limits).
- Switching to "lock every time" locks at once (the soft lock: the PIN or the gate reopens Sixkey), so a key already stored for other pages does not outlive the choice. Since 2026-11-24 no other change of the lock mode locks: the new mode decides the next lock.
- Lock now (the popup's header) and the `lock` keyboard shortcut (Alt+Shift+L by default, a manifest command handled by the service worker, so it works with no Sixkey page open) lock at once. Every lock tells open pages through the lock counter, and they drop the opened vault and the codes on screen at once.
- Soft and hard locks (QUICK-UNLOCK §5.5): Lock now, the shortcut, the idle timer and the screen lock are soft: the PIN, or the Touch ID / Windows Hello gate, still reopens Sixkey; with both set up either opens (OWNER-DECISIONS/17). A change of lock mode is soft for both (since 2026-11-24; before, it was hard for the gate). For the PIN a browser restart and an extension reload are soft too (its record is on disk: "Quick unlock: the PIN"); for the gate they are hard. The 5th wrong PIN in a row (it ends the gate too: someone is guessing at the keyboard), "End quick unlock and lock", declaring the profile shared and a key change are hard: the master password first (after a key change made on the settings page, the PIN alone there for 10 minutes). Removing the last gate passkey ends the gate's quick unlock, not the session of the settings page that removed it, nor the PIN. A passkey that opens Sixkey after a restart is not affected by either; it asks for the master password every 14 days, and a key change pauses it, and a gate too, until it is turned back on.
- **The side panel** (optional, off by default: Settings › Appearance › "Clicking the icon opens", or "Open in side panel" in the popup's header) draws the popup's screens in a page that stays open beside the web page, so it would otherwise keep the unlocked window open for as long as it is open. It is treated like the settings page: Sixkey locks (the soft lock, as the idle timer's: a live PIN stays) after 15 minutes in which the unlocked key's record of activity did not move, whatever the automatic lock allows. The panel moves that record only on the user's own input in it, not on its redraws or on changes made elsewhere; other pages move it when the popup opens or a settings page loads the vault (typing in a settings tab does not). In "lock every time" mode the key is the panel's own, and it is dropped from the panel's memory at that point and when the panel closes, without locking other pages. In the other modes closing the panel ends its page but not the shared key, as closing the popup does not. A secret typed on the panel's lock screen, or a Show box ticked there, is wiped after 2 minutes without input and when the panel is hidden. An unlock in another page opens the list at once only in a panel used in the last 5 minutes; a panel left alone stays locked until the user's next input in it. The panel is never offered in a profile declared shared: the service worker does not enable its page there, and the page closes itself if it is opened anyway. It is a separate extension page with its own sender row (`src/platform/sender-policy.ts`); it reads the clicked tab's address through `activeTab`, as the popup does, and no other tab's; on another tab one line says to click the icon there (docs/design/notes/SIDEPANEL-NOTES.md).
- **Security mode** (Settings › Security › Security mode, and the first-run question) bundles three settings:
  - _Only me (standard)_: lock after 15 idle minutes and when the screen locks; codes visible.
  - _Shared, cloud-synced or script-controlled_: lock every time the popup closes and when the screen locks; codes hidden. The first-run steps then offer to turn on Clear clipboard.
  - Changing any of the three shows "Custom". Which mode is current is never stored; it is read off the settings.
  - Asking for the master password before every export is not part of either mode: it is always on.

## Quick unlock: the PIN

- **What it is.** After you set a PIN (Settings › Security › PIN quick unlock, behind the master password or the PIN in force; or first run's PIN step, right after the vault is made, without the master password typed again, since it was typed on that page minutes before: only by the page that made the vault, within 10 minutes, once, before any PIN is set up, in a solo profile, and never after a recovery-key restore that kept the backup's master password), a 4 to 8 digit PIN reopens Sixkey after it locks. The master password always works. While the PIN opens Sixkey, exports, deleting for good, clearing the security record, a new recovery key, setting, changing or removing the PIN and Touch ID / Windows Hello ask for the PIN again (since 2026-11-24, counted with the lock screens' 5 tries; "Use master password" is always one click away); key changes (a new master password, a new key) ask for the master password, which the new key is wrapped under.
- **Where it lives.** `sk_pin` (`chrome.storage.local`): the PIN's set-up, a key derived from the PIN (PBKDF2-SHA256, 600,000 iterations) encrypted under your vault key, so a copy of the profile cannot test a PIN against it without the vault key. `sk_pin_restart` (`chrome.storage.local`, this profile only, never synced, backed up or exported): the PIN's record, made when the PIN is set: the vault key under AES-256-GCM with a key derived from the PIN's own key (PBKDF2-SHA256 at the master password's count, 2,000,000 iterations at least, on top of the PIN's 600,000), bound to the vault, the vault key, the record, the PIN's set-up and the keyring's wraps, a MAC under the vault key, and the wrong tries in a row. The PIN, the keys derived from it and the opened vault key are never stored. **A copy of the profile can guess the PIN offline from it** ("What it protects, and what not"). Since OWNER-DECISIONS/20's second 2026-10-30 note this record is the PIN's only way (docs/design/notes/PIN-RESTART-NOTES.md §18): before, by default the PIN worked only from session memory (`sk_quick`) until the browser closed, for at most 12 hours, and the record only with the "Also after a restart" switch, for 14 days at a time. `sk_quick` (memory only) now holds only the Touch ID / Windows Hello gate's arming.
- **When it works.** After any lock, also after the browser restarts or the extension reloads (a store update too), with no time limit, while the keys are the ones its record was made for. Never in a profile declared shared or script-controlled (the security mode). **The one limit: 5 wrong PINs in a row.** Each try is written to the record before it is derived, so a closed popup, a restart or a reload gives no fresh tries; a right PIN takes the count back to none; the 5th wrong one takes the encrypted key off the record (no key material is left on disk) and the next master password typed on a lock screen makes it again (a recovery key does not). **A key change** (a new master password, a reset, a new recovery key, a rotation, one taken from sync) **pauses** it: the PIN alone turns it back on in Settings within 10 minutes of a change made on that page (with sync on too); otherwise the next master password typed on a lock screen makes it again for the new keys, by itself. "End quick unlock now" takes the encrypted key off too, until the next master password. Removing or changing the PIN (a changed PIN gets a new record), declaring the profile shared and a new vault (a restore, Start over) delete it.
- **Updating from before 2026-10-30.** A record made with the old "Also after a restart" switch is kept and used as it is; its 14 days are gone. A PIN set without the switch (its arming was only in session memory) gets its record from the next master password typed on a lock screen: the PIN need not be set again. Until then the lock screen says the PIN works again once you type the master password.
- **The lock screen says when it waits.** With a PIN set up for these keys whose record does not open Sixkey now (after 5 wrong PINs in a row, "End quick unlock now" or a key change, and for a PIN set before 2026-10-30 until its first master password), the popup's and side panel's lock screen, and the settings page's unlock bar, say in one line that the PIN works again once you type the master password. It comes from what the lock screen already reads (`sk_pin`, the record and the settings, inside the pointer's read; nothing more from `chrome.storage.local`), and is never shown in a profile declared shared. It tells someone at the lock screen that a PIN is set up, as the PIN screen itself does whenever the PIN works.
- **What it protects, and what not.** It stops someone at this computer, who gets 5 tries in a row. It does **not** stop a copy of the profile, a program running on this computer or anyone who opens the browser's developer tools: they can copy the record and guess the PIN offline, every 4-digit PIN in a few seconds on one high-end graphics card (the table at the top), so for them a Sixkey with a PIN is only as strong as the PIN. Settings says so where the PIN is set. Don't reuse your phone or bank PIN: whoever holds your vault key could recover it.
- **Deleting for good** (the trash's "Delete forever"; the Sync section's deletes of kept vaults and parked saves went with that section, and the server sync's kept vaults with its client) always asks again when there is a master password: the PIN while it opens Sixkey (since 2026-11-24), or the master password, so an unlocked page left alone never reaches it.

## Quick unlock: Touch ID and Windows Hello

- **What it is.** Settings › Security › Unlock with Touch ID (Windows Hello on Windows) adds this computer's sign-in as a way to open Sixkey, behind the master password typed again. Chrome asks twice: once to make a passkey, once to check it. The master password always works, and exports, key changes, deleting for good, and adding, removing or turning back on a passkey still ask for it (docs/design/notes/PRF-NOTES.md).
- **Two kinds, decided by what the passkey returned, never by the computer's system.** A passkey that gives Sixkey a key of its own (the WebAuthn PRF extension) opens Sixkey **also after the browser restarts**: `sk_prf` holds the vault key encrypted under a key derived from that passkey's PRF output (HKDF-SHA256, AES-256-GCM, bound to the vault, the vault key and the passkey). One that gives none (Touch ID through Chrome's own profile store, for one) is a **gate**: it reopens Sixkey after it locks, until the browser closes, as the PIN does (beside it when both are set up); Sixkey keeps only its public key, with a MAC of it under the vault key, and checks every answer itself (our challenge, our origin and RP ID, the user present and verified, the signature); a key change pauses a gate until it is turned back on, as it does the other kind (right after a key change made on the settings page, with one touch and no second password; anywhere else with the master password). A synced gate can be made one that also works after a restart, in place, after the notice and one touch.
- **Passkeys that sync** (iCloud Keychain, Google Password Manager, a password manager) are used across restarts only after you tick "Allow a passkey that syncs" and read what it means; otherwise they are used as the gate. On a Mac, Chrome's Touch ID with a key of its own is only available through those (measured in Chrome 154, macOS 27). Never offered in a profile declared shared.
- **Every 14 days the master password**, so that you do not forget it: after that the persistent unlock asks for it once. A recovery key unlock does not count. This is a reminder enforced by Sixkey, not a security control: anyone who can write the profile's storage can move it.
- **What it protects, and what not.** The persistent kind adds nothing a copy of the profile can use without the passkey and its user verification; the copy is still exactly as strong as the master password (and see the synced row above). The gate: like the PIN, it stops people at this computer and not programs on it or the browser's developer tools; the vault key it reopens is in session memory. Whoever can sign in to this computer as you can open Sixkey with either: that is the equivalence asked for.
- **Removed or lost.** Removing a passkey from Sixkey asks for the master password and does not delete it from the system or the passkey provider (the box says where it is). A passkey deleted there, a reinstalled system or a profile moved to another computer simply stop working: the master password and the recovery key still open Sixkey, and the box offers to remove what no longer works. Nothing is lost.
- **The extension ID.** A passkey belongs to `chrome-extension://<id>`: a copy of Sixkey with another ID (unpacked, a dev build) cannot use passkeys made for the store's, and falls back to the master password.
- **Windows Hello is unverified on real hardware.** The Windows half is built to the same rules and classified the same way, but has not yet run on a Windows PC (OWNER-CHECKLIST item 35, PRF-NOTES.md §12): what this section says of Windows Hello is what is expected, not what was measured.

## Hidden codes, "This site", adding from the popup (U1, H7)

- **Hide codes in the popup**: a hidden row holds no digits in the page, only a mask. A click still copies the code. Holding the button (450 ms) or pressing Space shows the selected row's code for 5 seconds. The codes are still computed in the popup's memory, and a copied code is on the clipboard: this keeps codes off the screen, not away from anything that can read the page, the clipboard or the debugging port.
- **"This site"** is shown only for an account whose registered sites include the page's host name, or a parent of it on a label boundary (`github.com` covers `gist.github.com`, not `notgithub.com` or `github.com.attacker.io`). Host names are compared in the ASCII (punycode) form the browser gives, so a look-alike in another script never equals the real name. A guess from the account's name only puts it under "Possibly related", never labelled, and not at all for an account that has a registered site. A registered site covers every address under it: register the shortest name only if all of it belongs to that service.
- **Registering a site** ("Remember: <host> belongs to this account", the Sites field in the editor, or "Show first on <host>" when adding) saves the chosen host name (the page's host or a parent of it) into that account, inside the encrypted vault. Single labels and shared suffixes such as `co.uk` or `github.io` (a built-in list) cannot be registered. "Remember" is under each "Possibly related" account (never one that has a site of its own) and, on any page no account is registered for, under every account after the list's "Which account for <host>?" → Choose: accounts already registered for other sites too, and on look-alike pages too (on `github.com.attacker.io`, GitHub registered for `github.com` is offered). The sheet starts with the page's own host ticked (`github.com.attacker.io`; its parents, such as `attacker.io`, are the other choices) and, for an account that already has sites, names them above its Remember button ("This account is already remembered for github.com. Remember only if this page is the same service."): a warning, never a block. Remember a site only on the real one.
- **Adding from the popup**: text or a QR screenshot pasted into the popup (Ctrl+V), or a scan of the page ("Scan QR code on this page" in Add account, "Scan this page" on the empty list), goes straight to the popup's confirmation screen. Scanning captures the visible part of the tab (allowed by `activeTab` while the popup is open), decodes it in memory and discards the image. Nothing passes through `chrome.storage.session` any more. "Continue in Settings" opens the settings page without carrying the text; it is pasted again there. The settings page still contains the old reader for a scanned link in session storage (`AddAccounts.tsx`, at `#add-scanned`): nothing writes that key any more, and `test/e2e/firstrun.spec.ts` uses it only to check that a new install cannot add an account that way before it has a master password.
- **Adding from a file or the camera** (Settings › Add account; `docs/design/notes/IMPORT-FILE-NOTES.md`): a file the user chooses or drops is read in memory, recognised by its content, and only its accounts' checked `otpauth://` links are kept until the import is added, cancelled or Sixkey locks; its keys are never shown on screen (nor are the codes the camera reads), and a skipped entry is named by issuer and account only; an entry whose parameters cannot be read is refused, never given the defaults. Encrypted exports of other apps are recognised and not opened. The camera runs in the settings tab only (`getUserMedia`, Chrome's prompt for the extension's origin, no manifest permission); frames are decoded in memory and dropped, and every way out (a code read, Cancel, the tab hidden, the page left, a lock) stops the camera. After an import that added accounts from a file, Sixkey offers to delete that file: only on the user's click, only the file the user picked (its handle from Chrome's picker or the drop), after Chrome's write prompt, and only if it is unchanged since it was read (size, time and the SHA-256 of its bytes); the prompt says how many of the file's entries were not imported, and how many came in as HOTP. Deleting is not secure erasure: on SSDs and APFS the data may remain recoverable, and copies elsewhere (cloud sync, backups) are untouched; without a handle the page says how to delete it by hand.
- **Duplicates** are judged by the decoded key bytes. On the settings page an account is a duplicate only when its codes are the same as well (type, algorithm, digits, period): the same key with other parameters is added. "Replace" (a site gave a new key for an account) moves the old account to the trash in the same save; nothing is ever replaced automatically.
- **Plain key lines** (Settings › Add account): a key alone, or `name|key`. With more columns, Sixkey reads only the key column (found automatically or chosen) and a name column. Every other column, such as a password, is dropped: it is never saved, and the preview reports only each column's position, length and whether it looks like a key, never its content. A line of letters could be read as a key; it must be at least 16 base32 characters, and nothing is added before the user confirms.

## Exports and the master password (H2, H3)

- **Every export asks for the PIN or the master password again**, even while unlocked (the PIN since 2026-11-24, when one opens Sixkey now: `RestartAdmin.confirmPin`, counted with the lock screens' 5 tries; otherwise, or by choice, the master password): the encrypted backup, the plain text list and "Export selected accounts". The service checks it against the keyring as stored now (`verifyPassword`), without touching the unlock session; a wrong one is refused and recorded in the security record. A Phase 0 vault without a master password has nothing to ask for: the page warns and exports.
- The typed password is emptied after each attempt, when Sixkey locks (from any page), when the tab is hidden, and after a minute without typing.
- **A new recovery key** also asks again (the PIN, or the master password), because a recovery key resets the master password. It is a key event: the PIN pauses until it is turned back on in Settings (the PIN alone, for 10 minutes) or the next master password.
- The export is made from the vault as stored at that moment, not from the copy the page loaded. Each export is recorded (kind and time) once the file exists, before it is handed to the browser's download.
- **Export selected accounts** (H2) writes an ordinary encrypted backup file (`sixkey-backup` v1) with its own password, which must differ from the master password (compared after NFKC normalisation). It holds only the ticked accounts that are alive (nothing from the trash, no other account's name, group or sites), under a new random vault id and new account ids, with every creation time and edit stamp set to the export time by a clock with a new random device id; groups and registered sites of the ticked accounts go with them. If the ticked accounts changed in another page since this one showed them, nothing is saved and the page reloads. What a file still reveals: the accounts it holds; that it is a selected-accounts file, once opened (all its times are equal) and by its default name `sixkey-selected-<date>.json`; the order the accounts had in the list; and roughly its size, since it is not padded (two exports of the same selection have the same length; full backups are no different).
- **Limits of H3**: the check runs in Sixkey's own pages and service. It stands against a person at an unlocked browser who does not know the master password. Anything that can run code in those pages (A10, malware) skips it.

## The security record (H6)

- What it holds: the time and kind of each wrong master password (at the lock screen and wherever the password is asked again), each wrong recovery key, each accepted recovery key, each export by kind, each key change (master password turned on, changed or reset, recovery key renewed, key replaced), and one line when it is cleared. No account names, codes, passwords or error text. A recovery key or password that is not even well-formed is a typo and is not recorded. At most 50 entries; wrong guesses and other events each keep at least their newest 25.
- Where: under its own key in this browser profile's `chrome.storage.local`, with its own lock. Sixkey never sends it, never puts it in the IndexedDB mirror, backups, exports or the diagnostics file. A browser that syncs or copies whole profiles carries it along. Making, restoring or starting over a vault leaves it as it is: it is this browser profile's history, not the vault's.
- The popup reads it once, only after an unlock in that popup and once the first code is on screen, and shows "N wrong password, recovery key or PIN attempt(s) since you last saw this". The number shown is then taken off the count. Wrong guesses made while unlocked (before an export, say) are reported at the next unlock in the popup.
- Settings › Security › Security record lists the entries. Viewing it changes nothing. Clearing it needs the master password (a wrong one is refused and recorded) and leaves one dated "Record cleared" line. A Phase 0 vault without a master password needs none.
- It is an alert line, not evidence: anyone who can write the profile (a copy of it, malware, the debugging port of an unlocked browser) can edit or erase it.

## Install source (H4)

- The store build asks the browser how this copy was installed (`chrome.management.getSelf()`, which needs no permission), a moment after the page has drawn. A copy that was not installed the normal way (loaded unpacked, or put there by other software) gets a banner in the popup and at the top of the settings page, with this copy's extension ID to compare. A copy installed by an administrator's policy is never flagged. The store build carries Sixkey's store ID (`extension/scripts/store-id.mjs`), so a normally installed copy with another ID, such as one installed from a `.crx` file, is flagged too. The last answer is kept in the page's `localStorage` so the banner can appear in the first frame. Dev and test builds do not check.
- Until Sixkey is in the store, every unpacked copy of the production build (`npm run build`, `dist/`) shows the banner, including the one the owner loads to test.
- It finds old sideloaded copies that never update. It cannot catch a modified copy: such a copy can simply remove the check.

## Storage and the "never lose data" design

- Two slots plus a pointer in `chrome.storage.local`. A save writes the **inactive** slot, reads it back and compares it, and only then flips the pointer.
- Rolling snapshots of the last 10 changes, daily snapshots for 7 days, a copy of the keyring, and a second full copy in IndexedDB (the mirror) with up to 7 daily snapshots.
- Startup order when something is wrong: the other slot, then whichever surviving copy (a snapshot or the mirror) has the highest save counter. Every restore from a damaged slot, a snapshot or the mirror is recorded and shown to the user, with the time it was restored to. Not shown: a missing pointer is fixed quietly; a save that reported an error after its slot was written can become current at the next browser start; and an unfinished key change that is rolled back leaves only a diagnostics line (see below).
- Verified by tests, for faults injected into the primary store: a crash (before, after, half, or torn) at every single write of a save never loses a saved state; random single faults on any stored key are survivable; with both slots destroyed the data comes back from snapshots; with the primary store wiped it comes back from the mirror. A read that fails (as opposed to a slot that is read and found damaged) is reported and never "repaired" over. Faults in the mirror are not injected the same way: the mirror is best-effort by design, and a failing mirror never fails a save.
- Snapshots and recovery sources are ordered by a save counter, not by the clock, so a system clock that jumps backwards cannot make an older state look newer. (Only the choice between the two keyring copies, the keyring copy and the mirror's, goes by save time.)
- Anything Sixkey saves is checked first to be something it can load back (field lengths and shape). Otherwise a save that "worked" would look like corruption on the next read and be rolled back; the importer reports oversize lines instead.
- **Opening the popup reads little** (U1b): in the normal case, the pointer with the notices and the clean-up state in one read, the active slot, and the settings; no snapshot and nothing of the mirror. `test/unit/read-budget.test.ts` holds this to at most 4 reads of `chrome.storage.local` per opening and 8 for an unlock, the same with 2 or 17 snapshots.
- **Old key material after a key change.** A save that changes the keyring (a new key, the device key removed, a new password or recovery wrap of the same key, or a vault written over unreadable data) first writes a marker, before it commits. The clean-up then rewrites the other slot, the keyring copy and the mirror, and re-encrypts or drops the snapshots; once everything is under the current key, the marker is removed. A page that changed the keys runs it right after the change; an interrupted clean-up, and the one after a vault written over unreadable data, run at the next popup opening or unlock. A store last written by a version before the marker gets one full check. Independently, the self-check at browser start (and at install or update) overwrites a device key left in the other slot, the keyring copy or the mirror.
- **What the clean-up keeps.** A snapshot under a key that is neither the current one nor listed as a previous one is kept only if it belongs to the same vault (the same vault id): for example one under a newer key after an unfinished key change was rolled back, or the remains of an unreadable vault after a backup of the same vault was restored over it. Those are kept because a keyring that opens them may come back once sync exists, reported in the diagnostics log, and age out under the normal snapshot limits; the clean-up no longer discards them as the earlier full scan did. A snapshot of another vault under an unknown key (after "start over", or after restoring a backup of a different vault over unreadable data) is dropped by the clean-up that follows, at the next popup opening or unlock.

### Interrupted key changes

Turning on or changing the master password, a new recovery key, replacing the key, and the password reset are each one locked save. Until that save commits, nothing has changed: if the browser or the computer stops before the commit, the next start does not commit the newer slot (it holds a different keyring) and rolls the change back, and a change whose save reported an error is taken back out of its slot as well. The old password and recovery key keep working. After the commit, a new recovery key goes to the page first, then the security record entry is written, then the unlock session, then the clean-up; a page closed during the clean-up has already shown the code, and the marker finishes the clean-up later. The service hands out a new recovery key only through that callback or, for a new vault (`prepareKeys`) and the password reset (`prepareReset`), before anything is written. The password reset (a forgotten password, with the recovery key) runs in a settings tab, because the popup closes when focus leaves it: the new password is typed twice, the new recovery key is shown, and only "I have saved it" and Continue write it; a tab closed before that changes nothing, and the code it showed opens nothing. Two residuals remain. A crash in the short window between the commit and the code reaching the page (the rest of that same save: the keyring copy, the mirror and, after a new key, a snapshot) leaves the change in force with the new code never shown; the password still opens the vault, and Settings › Security makes a new code. And if a power loss drops the commit's last write after the change was shown as done, before its clean-up finished, the next start rolls it back: the old password and recovery key work again, the new ones do not, and nothing on screen says so yet (see Known gaps).

### Limits you should know about

- `chrome.storage.local` and IndexedDB are both LevelDB-backed in Chrome. They are separate stores, not separate engines. Chrome may repair or **delete the whole database** after corruption, which takes the slots, snapshots and keyring copy with it. The IndexedDB mirror, the exported backup and the backup in Chrome sync (where Chrome syncs it) are what survive that. Back up regularly; the popup reminds you after 7 days.
- In some antidetect ("fingerprint") browsers the mirror is not an independent copy. GoLogin's SDK deletes a profile's IndexedDB every time the profile stops, and BitBrowser and AdsPower do not sync IndexedDB unless that option is turned on (`docs/research/fingerprint-browser-security-lessons.md`: GoLogin's SDK source and BitBrowser's API documentation were checked; AdsPower's setting comes from documentation that was not re-checked; GoLogin's desktop app was not checked). There the mirror is either empty at each start or does not travel with the profile, and the only copy that does not depend on the profile's own storage is an exported backup file.
- If this profile's IndexedDB fails on every access, a vault whose slots or local snapshots can be read keeps working, but a profile with no vault yet cannot create one: the check for data left behind needs IndexedDB, so the page shows an error and Retry. A profile whose vault cannot be read at all gets the same error instead of the restore and start-over choices.
- A power loss that drops writes `chrome.storage.local` had already reported as done can lose the last save. If IndexedDB kept the mirror copy of that save, the next self-check still overwrites it with the older slot.
- LevelDB and IndexedDB do not overwrite in place. After a value changes, the old bytes can remain on disk until the database compacts. That is why turning on the master password **replaces the key** instead of only deleting the device key: a leftover copy of the old keyring is then worth little. It also means deleting or purging an account does not securely erase it from disk.
- **Restoring over an unreadable Phase 0 vault.** Restoring a backup of the same vault over the unreadable remains of a vault that had no master password keeps that vault's old snapshots (see "What the clean-up keeps") under its old device key, until 10 more saves and 7 more daily snapshots push them out (the mirror's daily copies likewise). Whoever holds that old device key (from leftover database bytes, an earlier copy of the profile, or a damaged slot before the clean-up overwrites it) can open them without a password.
- JavaScript cannot reliably zero memory. The unlocked key exists in memory for as long as the vault is unlocked, and may be swapped to disk by the operating system.
- **An open page keeps what it has opened.** A page that is already open keeps the accounts it decrypted (and the popup its codes) in its memory and on screen until it is closed or loads its state again; a lock from a timer, the screen lock or another page does not clear it. In "lock every time" mode an open settings tab also keeps the vault key in its memory: nothing in that page runs on a timer, so the 15-minute idle limit is checked only the next time the page uses the key, and a screen lock or a lock from another page (a lock counter that every check consults) also takes effect at that next use. Until then the key stays in that page's memory, where the debugging-port case (A10) can read it. Close the settings tab when you are done.
- The idle timer and the lock-on-screen-lock use alarms and the `idle` permission. A service worker can be stopped by the browser, so every unlock check also compares timestamps rather than trusting a timer alone.
- Settings are not protected by the master password: anyone at the browser, locked or not, can change the lock mode, hidden codes and the display.
- Someone who can write the profile's storage (offline, or with the browser's developer tools) can add a Touch ID / Windows Hello gate credential of their own authenticator to `sk_prf`. It is listed in Settings › Security, but it never opens Sixkey: every gate credential carries a MAC under the vault key, made by Sixkey when it was added or turned back on and checked before it is ever asked for, and one without a valid MAC is never offered to the OS dialog. What it can still do: until the next master password, the lock screen may show a Touch ID button that disappears at its first press, with no OS dialog (the gate's arming is dropped then; the PIN, its own record, is not touched), and each master password parks the vault key in session memory for the gate, as a real gate would. They can also move the 14 days of the persistent unlock, or remove a credential, which only takes a way in away.
- Someone who can write the profile's storage can also move the PIN's count of wrong tries back to none (more tries at the keyboard), put back an older copy of the record (while the keys and the PIN's set-up are still the same, it opens again with that PIN), or plant a record of their own. A planted one never opens Sixkey (it cannot wrap the vault key without it) and costs only wrong tries; nothing ever renews it or makes it into one that opens (the master password's note, turning it back on and the settings page check its MAC under the vault key before they use it): the next master password typed on a lock screen replaces it with Sixkey's own, and the settings page removes it. A PIN change removes whatever is stored there and makes a new record. A record of other keys or another PIN set-up is never tried. Whoever can write the storage can also simply copy the record and guess the PIN offline, so none of this is a control against them (docs/design/notes/PIN-RESTART-NOTES.md §2.3).
- Deleting the PIN's record (removing or changing the PIN, a shared profile, a new vault), or its encrypted key (the 5th wrong PIN, "End quick unlock now", a key change), deletes what the browser's storage holds; LevelDB keeps the old bytes in its files until it compacts them (as for the Phase 0 device key above). A copy of the profile taken in between may still hold the old encrypted key and allow guessing the PIN offline, and with it the vault key of that time. A key change protects only what is added after it (the old bytes of the vault itself, under the old key, may sit in the same database files); for the accounts already in Sixkey, only re-issuing their 2FA keys at each service makes such a copy worthless, as for the Phase 0 row above.
- The trash is never emptied automatically: a wrong system date must not be able to erase accounts. After 30 days the settings page offers one button to erase the old items. "Delete forever" removes the secret from the vault and from every copy Sixkey keeps (previous slot, snapshots, mirror, and the vaults a sync join kept aside, when a key this profile holds opens them; one kept under a key this profile no longer holds, after starting over for example, is left as it is: the trash says so at that moment, and only deleting it in Settings › Sync removes it. Whoever has that old sync account's master password and its server could still open such an entry). If the browser stops after the account was erased from the vault and before the copies were rewritten, nothing retries: the older copies keep it until they are replaced in the normal way (the other slot at the next save, rolling snapshots after 10 more saves, daily ones after 7 more daily snapshots). The same holds for the IndexedDB copies if IndexedDB fails during the purge. It does not touch files you exported, and old bytes may remain in the browser's database files until it compacts.

## Clipboard

Copying a code needs no permission. Clearing it 30 seconds later, **only if the clipboard still holds that code**, needs the optional `clipboardRead` and `clipboardWrite` permissions, requested from the settings page, plus an offscreen document to hold the timer. Only a SHA-256 of the code travels between parts of the extension. (A 6-digit code has few possible values, so that hash does not hide the code from anything that can read the extension's messages; it only keeps the code out of the message itself.) A browser cannot "copy nothing", so a single space replaces the code. Clipboard history tools (such as Windows Win+V) may keep their own copy. Pasting into the popup (Ctrl+V) reads only what the user pastes, through the paste event, and needs no permission.

With the session's key while unlocked, the worker's shortcut makes the gate's verified read, which may merge a pending overlay (a tagged write in the worker).

**The grant record.** The switch is kept in one record, `sk_plugins`, tagged with HMAC-SHA256 under a key derived from the vault key (`HKDF(vault key, "sixkey/v1/plugin-grants")`), binding its entries, `developerMode` and an epoch; without the unlocked key nothing is read from it but autofill's switch, tighten-only. It was the plugin platform's record of every plugin's approval; since that platform was removed (2026-11-12) it holds autofill's entry alone: an entry an earlier version stored for another plugin still reads (the tag covers it, so the record verifies as before), is honoured by nothing, and is left out of the next record written, as are its overlay entries and pauses. What is decided without the key goes to an overlay that can only suspend, disable or remove. A read checks the tag under the current vault key only; after a key change the key-change cleanup re-tags the record under the new key (one of its VkRecords), and only there does a retired key count. A tagged write checks inside the vault lock that its key is still the vault's active one, so a page that stayed open across a key change writes nothing under the retired key and asks for the key again; and when the record does not verify under its key while the change's clean-up is still due, it writes nothing, tries again a few times over about 3 s, then asks the user to. A new vault (the first run, a restored backup, Start over) always has a new vault key, so the record left beside it is replaced when the vault is made, keeping autofill's Off. Nothing is kept aside: a record whose tag failed is replaced by the next tagged write, keeping the switch as read from it, and a copy an earlier version kept aside (`sk_plugins_unverified`) is removed then. The record is never synced, backed up or exported.

Touch ID and Windows Hello use WebAuthn from Sixkey's own pages and need no permission; the small window the toolbar popup opens for the dialog on systems other than macOS is `chrome.windows.create`, which needs none either. No other host permission, no `tabs`, no declared content scripts (one script registered to run by itself, only on the sites the user turned on; "On all sites" chosen in Chrome's extensions menu turns on no site, only the user's list counts), no `nativeMessaging` or any other way to talk to programs outside the browser, no remote code, no analytics. The service worker answers only Sixkey's own pages, each page only for the messages that page may send (`src/platform/sender-policy.ts`), (a script injected into a page by `scripting` would carry Sixkey's ID, so the ID alone is not enough). No other extension and no web page can message it: the manifest has no `externally_connectable`, so no web page can try, and while Chrome then lets any extension try, no build listens for another extension's messages or ports (`check-dist` refuses `onMessageExternal` and `onConnectExternal`), so the attempt fails as for an extension that is not installed; there is no `management` permission either. At every start the service worker also asks the browser to close `chrome.storage.local`, `chrome.storage.session` and `chrome.storage.sync` to scripts that are not Sixkey's pages or worker (`TRUSTED_CONTEXTS`), for reads and for writes; `storage.sync` holds the backup in Chrome sync (the encrypted vault as on disk), which the worker writes only in a run of it whose start had that call accepted: where the browser refuses it, no backup is written there (turning the backup off and a merge's removal still remove copies), and Settings › Backup says why (checked for `sync` by the browser probe, test/e2e/csb-probe.spec.ts, in Chromium 156 and in part 145). What protects against a content script is the browser keeping that setting, not the order of the worker's start. It was checked in Chromium 145 and 156 only (an independent review: both refused after the call, and still refused after a browser restart). Before Chrome 140 `storage.local` cannot be closed at all: its `setAccessLevel` exists only from Chrome 140 (Chromium commit a8f1f337), so there a script injected into a page could read and write the encrypted vault. Autofill therefore injects nothing into any page unless both areas were just confirmed closed (asked again before every injection, never remembered); since wave 1b of the plugin platform Sixkey requires Chrome 140 (`minimum_chrome_version`), so this check is the second layer, and where a browser still refuses the call it shows "Autofill needs Chrome 140 or later" instead of the Fill button. `storage.session` is closed on every version. Chrome 140 to 144 and the case of an extension update are not checked. If the browser refuses the call, the worker still runs and writes one line to the diagnostics file. Fonts are bundled. The keyboard shortcuts (Alt+Shift+K opens the popup, or the side panel in that mode; Alt+Shift+L locks Sixkey; Alt+Shift+F fills the code of the one account registered for the page, or opens Sixkey to choose; all changed at `chrome://extensions/shortcuts`) are manifest commands, not permissions; `chrome.management.getSelf()` and `chrome.commands.getAll()` need none.

## Known gaps and open decisions

- The strength estimator `zxcvbn-ts` is a third-party dependency (it is not cryptography) and runs only in the settings page. For the master password it refuses under 10⁶ guesses and only warns between that and 50 bits (OWNER-DECISIONS/15); for a backup file's password it is the bar, so any future caller of the backup code must run it first, since `createBackup` enforces only the floor. This is an open decision.
- Before a release can turn the server sync on again (its client is removed, DV-0b: a paid cloud would bring one back), turning it on must either check the password's strength or require the account key held by the device (OWNER-DECISIONS/15's precondition; `docs/SYNC-DESIGN.md` §9 item 17). Turning sync on uploads the password as it is, and the server's `password_verifier` is PBKDF2 at 600,000 iterations whatever the wrap's count, so a leak of the server's database would be an offline guess at it. Today it holds because no build can turn sync on (OWNER-DECISIONS/25); the 50-bit bar on the sync key operations does not.
- Reading a QR code from the page (popup → "Scan QR code on this page") depends on `activeTab`, which only the real toolbar popup gets. The automated end-to-end suite opens the popup as a tab, so it does not cover this, nor the ranking by the current tab's address; both are owner checks. For the side panel, the suite clicks the real toolbar action through the DevTools protocol in headless Chromium and checks that the panel reads the clicked tab's address and no other tab's (`test/e2e/sidepanel.spec.ts`); the scan from the panel is still an owner check.
- An unfinished key change that is rolled back at the next start (see "Interrupted key changes") leaves only a line in the diagnostics log. A notice that says so is planned before release.
- In the popup, a failed edit, delete or drag-to-reorder says nothing: the edit dialog stays open with no message, and a failed move leaves the order as it was. (Remembering a site does report a failure.)
- "Replace key" fails without writing anything once the keyring already lists 64 previous keys (every new key, including the one made when a Phase 0 vault got its master password, adds one).
- The "backup saved" notice and the 7-day reminder reset happen when the file is handed to the browser's download, because an extension page cannot tell whether the user then saved it. The backup in Chrome sync resets the reminder too, at each copy handed to Chrome's sync storage, though Sixkey cannot tell whether Chrome uploads it (no receipt; the card says so); and while it is on and has not stopped, the reminder does not show at all (a vault that has not changed is not handed over again, and its copy is the vault as it is).
- The recovery key can be copied to the clipboard or saved as a file. Both leave a copy on this computer; the text asks for a copy that survives losing it.
- HOTP accounts are stored and backed up, but cannot generate codes yet.
- The text of the _plain text export_ is unprotected by design; the UI warns, requires a checkbox and asks for the master password.
- Phase 1 (sync): the server sync's client, its engine and its network path, is removed from the extension (DV-0b; it
  can be found in the history). The design, its threat model and its residuals are `docs/SYNC-DESIGN.md`; the server
  (`api/`) and the contract stay. A dev or e2e profile that once had it on keeps its records, its identity's database
  and its alarms until that build's worker removes them at an install or an update (`src/platform/server-sync-leftovers.ts`): with them goes whatever a vault
  kept from before a join (`sk_prejoin`) or a save kept after a recovery (`sk_sync_orphan`) held, which no build can
  open any more.
